# ADR 0034 — 背景席は仕事の種類でモデルを選び、Opus の実装席は 1 席 1 仕事で道具出力を小さくし、繰り返しの下ごしらえはスクリプトにする

- 状態: 受理（設計リナ 2026-09-24。hide の運用変更の手 1・手 2（Issue #100）と手 3（同 Issue のコメント・記録 #106）を 1 つの運用 ADR にした。判断の裏は hide が 2026-09-22 の transcript を集計した数字と、2026-09-22〜24 の日報にある席の起動記録）
- 日付: 2026-09-24
- Issue: #100（記録 #104 / #106・chore #101 / #102 / #103）
- 影響する規則: GIT-001 / GIT-003 / GIT-004、ADR 0001（`planned` を `active` と書かない）。製品コード・ゲート・スキーマには触れない
- 関連: [実装席の指示書テンプレート](../IMPL_SEAT_BRIEF_TEMPLATE.md)、[開発の流れ](../DEVELOPMENT_WORKFLOW.md) §10、[引き継ぎ 2026-09-24](../handoffs/2026-09-24.md)

## 文脈

この repo の作業は、**設計席**（Claude Code の対話席。最上位モデル）が裁定・受理・仕様の文言を持ち、
**背景席**（`Agent` で立てる席）が実装・調査・記録を行う形で進めてきた（2026-09-11 以降）。
2026-09-22〜24 に hide が Claude Code の transcript（`~/.claude/projects/<repo>/**/*.jsonl` の assistant usage）を集計して分かったこと:

- **減っているのは Opus の枠**で、設計席（Fable）の枠とは別の財布である。Opus の消費は**全部が Agent の実装席**だった。
- 実装席は **1 席あたり 150〜400 ターン**、文脈が **350〜800K トークンまで太ったまま毎ターン読み直し**、
  cache read が **1 席 0.4〜1.7 億トークン**。費用は「ターン数 × その時点の文脈長」の積み上げなので、
  太った席を長く走らせるほど二乗で効く。
- 2026-09-22 の Opus の起動 **108 本のうち約半分**は実装ではなく、レビュー・ペルソナ・棚卸し・スクリーンショット撮影・
  checkout 準備だった。2026-09-22〜24 の調査・棚卸し・記録の agent（8 本）もすべて Opus で立てていた。
- 同じ下ごしらえ（実機用 checkout の準備・PR の統合手順・前後の絵の比較）を設計席が手で 4〜12 回繰り返していた。

つまり、減りの原因は 2 つある。**判断を含まない仕事まで Opus に出していること**（席の選び方）と、
**1 席が長く太っていること**（席の形）。前者はモデルの階層で減るが、後者はモデルを変えても減らない。

## 決定

**背景席は仕事の種類でモデルを固定し、Opus の実装席は 1 task を 1 席で走らせず道具出力を小さくし、
同じ下ごしらえを 2 回モデルに踏ませたら 3 回目は `tools/` のスクリプトにする。**

### 決定 1 — 席ごとのモデル（手 1）

| 仕事 | 席 | `model` |
| --- | --- | --- |
| 裁定・受理・採点・指示書と仕様の文言・保護対象（ゲート・閾値・スキーマ）の判断 | 設計席自身 | （対話席） |
| 実装（1 task = 1 branch = 1 PR）と差し戻し対応 | 実装席 | `opus` |
| 下ごしらえ: 現物調査メモ・棚卸し・出力の比較・実機用 checkout の準備・ペルソナの意見・報告との突き合わせ | 下ごしらえ席 | `sonnet` |
| 純粋な機械作業: テスト一覧の照合・差分の列挙・差分 0 の確認 | 機械席 | `haiku` |

- 判断基準は「**その仕事を間違えたとき誰が直すか**」。設計席が照合して直せる仕事は下のモデルでよい。
- 下ごしらえのメモは **300 行以内**・疑問一覧は **15 件以内**。ペルソナは **4 席まで**を Sonnet で各 **150 行以内**。
- 差し戻し 2 回目以降は指示を狭くする（変更 1 命題・再実行 1 集合）。
- ローカルの Ollama は Claude Code の Agent からは呼べない。使うなら別ランナーの補助席として XS / S の task に限り、受理は設計席が行う。
- 読み取り専用の ADR の批評と PR の独立レビューは**判断**なので、設計席自身か Opus に置く。

### 決定 2 — 繰り返しの下ごしらえはスクリプトにする（手 2）

- 同じ手順を **2 回以上モデルに踏ませたら、3 回目は `tools/` のスクリプトにする** chore を実装席に発行する。
- スクリプト化した手順は**設計席が直接実行**し、受理の独立照合は**スクリプトの実出力**を読む（モデル代ゼロ）。
- 発行済み: #101（実機用 checkout の準備: pull → build → SHA の記録。起動はしない）・#102（PR の統合: GIT-004 の字面検査 →
  Ready → CI 待ち → squash merge → main の ff）・#103（前後のスクリーンショットの画素比較。差分の外接矩形が指定矩形の内側かを JSON で返す）。
- `tools/` は製品の一部ではない。第三者の配布物を足さず（QLT-011）、`eng/` のゲートを呼び出すことはあっても弱めない（QLT-010）。

### 決定 3 — Opus の実装席の形（手 3）

- **3-1 1 task を 1 席で走らせない。** probe（現物調査）→ 実装 → 差し戻し対応を、それぞれ**新しい Agent** にする。
  引き継ぎは報告ファイル（`out/agents/<issue>-<仕事>/report.md`）で渡す。
  **SendMessage で同じ席を次の仕事に使い回すのは Opus では禁止。** `fork` は親の全文脈を継ぐので背景席に使わない。
- **3-2 道具出力を小さくする。** 文脈が太る原因はテスト全文・ビルドログ・ファイル丸読みが毎ターン残ること。
  テストは対象だけ実行し失敗行だけ tail する／ログはファイルへ落として grep で読む／ファイルは必要な範囲だけ読む。
  **最終報告は 30 行以内**。詳細は報告ファイルに書き、親にはパスと数字だけ返す。
- **3-3 task を小さく切る。** M 級 1 本より S 級 3 本。差し戻しは「変更 1 命題 = 新しい席」。
- **3-4 手 1 を守る。** レビュー・ペルソナ・棚卸し・撮影・checkout 準備は Sonnet / Haiku（または決定 2 のスクリプト）へ。
- **3-5 Opus 5.5 は試行扱い。** API 単価は Opus より低く同じトークナイザだが、サブスクの週間枠での重み付けは未確認。
  実装席で 1 日走らせ、枠の減りを見てから決める（決めるのは hide）。
- **計測して言う。** 枠の減りを疑ったら transcript の usage（cache_read / output / 最大文脈 / ターン数）を席ごとに集計してから手を選ぶ。
  数字で言えないうちは手を増やさない。
- 指示書の型は[実装席の指示書テンプレート](../IMPL_SEAT_BRIEF_TEMPLATE.md)。3-1・3-2 の文言はそこに固定してあり、席ごとに書き換えるのは穴だけである。

### 決定 4 — 施主指示の型

hide の指示は **Issue（台帳）→ ADR（判断）→ 引き継ぎ（再開点）** の順に写し、正本（`docs/todo/current.md` の「次の 1 手」）に 1 行を残す。
指示が届いたセッションで記録の PR を出し、判断そのもの（ADR）は次のセッションの最初の手にしてよい（#104 → #106 → この ADR がその形）。

## 強制

- 機械強制: **不能**（席の選び方・席の形・報告の長さは Claude Code の運用であり、この repo のゲートは transcript を読まない）。
- 代わりに次で守る: (1) 指示書はテンプレートの穴を埋める形でしか書かない。(2) 日報の「運用」節に、その日に立てた席を
  「Issue・仕事・model・報告ファイル」の 1 行ずつで残す（決定 1 / 3 の逸脱がそこに見える）。(3) 枠の減りを疑ったら決定 3 の計測を先に行い、
  その集計を日報に残す。
- `tools/` のスクリプトは `.ps1` として CNF-005（ゲートを無効にする語）・CNF-008（Issue 番号の無い task marker）の字句検査に入る（active・`eng/conformance.py`）。
  スクリプトの正しさそのものはゲートの外で、受理の独立照合は設計席が実出力で行う。

## 結果

- 得るもの: Opus の消費が「判断を含む仕事 × 短い席」に限られる。設計席の受理が 30 行の報告と実出力で始まり、
  報告ファイルは必要な範囲だけ読めばよい。繰り返しの下ごしらえはモデル代ゼロになり、実出力が受理の証拠になる。
- 失うもの: 席が増えるぶん、指示書を書く回数と、席のあいだの引き継ぎ（報告ファイル）の手間が設計席に移る。
  1 席の中で持っていた文脈（probe の細部）は報告ファイルに書かれた範囲しか次の席に渡らないので、**報告ファイルの質が席の質を決める**。
- 前提: 週間枠の減りの原因がこの集計どおりであること。**Opus 5.5 の枠の重みは未確認**で、試行の結果で決定 3-5 を書き換える（新しい ADR で）。
- 緑であることが証明しないもの: この ADR は運用なので、フルゲートの緑は「席の形が守られている」ことを何も証明しない。守られているかは日報の行と transcript の数字で見る。
- 移行: 既存の 28 本の作業木と統合済みの枝には影響しない。この ADR の受理と同じ日に #101〜#103 を決定 3 の形（3 席・各 1 仕事）で立てた。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| すべての背景席を Opus のまま、モデルの階層だけで減らす（手 1 だけ） | 減りの主因は席の長さと文脈の太さで、モデルを変えても「ターン数 × 文脈長」は縮まない（9/22 の集計） |
| 1 task を 1 席で probe → 実装 → 差し戻しまで持たせ、SendMessage で続ける | 席が仕事をまたぐたびに文脈が積み上がり、後半のターンほど高くつく。引き継ぎの損失は報告ファイルで補える |
| `fork` で親の文脈を継いだ席を立てる | 親（設計席）の全文脈を最初から背負うので、最も太い席から始まる |
| 実装席の報告を全文（差分・テスト出力・ログ）で受け取る | 設計席の文脈が太り、次の指示書が長くなる。受理に要るのは数字とパスで、詳細は報告ファイルにあればよい |
| 下ごしらえのスクリプト化をせず、毎回モデルに手順を踏ませる | 同じ手順を 4〜12 回踏ませていた。スクリプトはモデル代ゼロで、実出力がそのまま受理の証拠になる |
| Opus 5.5 へ今日いっぱい切り替える | サブスクの週間枠での重み付けが未確認。1 日の試行で枠の減りを測ってから決める |
| ローカルの Ollama を背景席に使う | Claude Code の Agent からは呼べない。別ランナーの補助席としても XS / S の task に限る |
| 枠の減りを感じたら手を足す | 数字で言えない手は、効いたかどうかも言えない。集計が先 |
