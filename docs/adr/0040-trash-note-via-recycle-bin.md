# ADR 0040 — ノートは専用の `ITransferSource::RecycleItem` で OS のごみ箱へ送り、失敗しても完全削除へ進まない

## 文脈

hide の裁定（2026-10-06）は「削除したノートは OS のごみ箱へ。履歴も一緒に。確認の箱は出さない」。ADR 0039 の決定 13 は 3 点
（編集中なら先に保存・履歴も一緒・送れると確かめられない場所では消さない）だけを固定し、API と失敗の形をここに委ねた。

実測（Windows 11 10.0.26300・D: は NTFS・`probe.c` / `probe_ifo.c`）:

- `SHFileOperationW(FO_DELETE, FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI)` は、ローカル NTFS のファイルもフォルダ（中に md 3 つ）も
  ごみ箱へ入れる（フォルダは 1 項目）。戻り値 0。ファイル 1 つで 1 回目 254 ms・2 回目 269 ms・その後 70〜100 ms、ファイルとフォルダを 1 回で 665 ms。
  COM の初期化は要らず、呼び出しの後にスレッドへ COM が残らない。呼び出し中に可視の窓は出ない。
- **ごみ箱が使えない場所では、黙って完全に削除する。** 同じファイルを UNC（`\\localhost\D$\…`）と `subst` のドライブ経由で渡すと、戻り値 0・`fAnyOperationsAborted` 0 のまま
  ごみ箱に入らずに消えた。**`IFileOperation` も同じ**（`FOFX_RECYCLEONDELETE` を立てても `S_OK` で完全に消える）。
- **全長 260 文字を超えるパスも、黙って完全に削除する**（`\\?\` 無しの 358 文字: 戻り値 0・ごみ箱に入らない）。`\\?\` 付きは短くても長くても戻り値 124 で何も消えない。
- `SHQueryRecycleBinW(根)` の HRESULT で場所を区別できた: ローカルの `D:\` `C:\` `E:\` は `S_OK`、`subst` の根と UNC の根は `0x80070003`、無いドライブは `0x80004005`。
- 部分失敗: 2 項目を 1 回で渡すと、存在しない項目があれば何も消えない（戻り値 2）。1 つ目が他で開かれていれば両方残る（戻り値 32）。
  **2 つ目が他で開かれていると 1 つ目だけ消える**（戻り値 32）。読み取り専用のファイルは確認なしで入る。
- どちらの API も shell32 にある。ole32 は要らない。

現行コード（批評で確認）: adapter の `compose` は常に `\\?\` 付きのパスを組む。改名は対象と親 4 段を再解析ポイントから守っている。履歴のディレクトリには
書き込み途中の `N.md.tmp` が残り得る。起動した後に「文書なし」へ戻る経路は無く、`save_note` は無題だけを断る。ノートのカーソルは選択そのものである。

## 決定

1. **API は `SHFileOperationW` の 1 本。** `IFileOperation` は使わない（「送れなければ失敗」にならず、ole32 と COM の初期化だけが増える）。
   旗は `FOF_ALLOWUNDO | FOF_NOCONFIRMATION | FOF_SILENT | FOF_NOERRORUI`。adapters に shell32 を `nenefolio_system_link` で結ぶ（`platformLibraries.adapters_win32` に既にある）。
2. **送れると確かめられない場所では呼ばない。** API の戻り値は「ごみ箱に入った」ことを教えないので、判定は呼ぶ前にしか置けない。adapter は 1 つの対象（md、または履歴のディレクトリ）ごとに:
   - (a) 対象を**削除の権利つき・共有なし**で開く（ADR 0022 の開き方。ディレクトリも同じ）。開けなければ `BUSY`（無ければ `ABSENT`）。
     対象そのものが name surrogate の再解析ポイント（シンボリックリンク・junction）なら `UNAVAILABLE`。
   - (b) 開いたハンドルから**実体のパス**（`GetFinalPathNameByHandleW`）を得る。親のどこかがリンクや `subst` でも、ここで実体の場所になる。
     実体が UNC（`\\?\UNC\…`）なら `UNAVAILABLE`。`\\?\` を外した形が、判定と API に渡す唯一のパスである（`compose` の `\\?\` 付きのパスは渡さない）。
   - (c) 実体のパスの根（`GetVolumePathNameW`）に対する `SHQueryRecycleBinW` が `S_OK` でなければ `UNAVAILABLE`。
   - (d) **長さ**: md は実体のパスが 260 文字未満、履歴のディレクトリは「実体のパス + `\1.md.tmp`（9 文字）」が 260 文字未満。満たさなければ `UNAVAILABLE`。
   - (e) ハンドルを閉じてから API を呼ぶ（開いたままでは共有違反になる）。閉じてから呼ぶまでの間の入れ替わりは防げない（「残る」に書く）。
   どれか 1 つでも満たさなければ**その対象を消さずに**返す。
   **未測定（B1 の probe が先に測る）**: (b) の実体のパスを渡したとき `subst` 経由の `data/` がごみ箱に入ること・リンクで UNC を指すカテゴリが (b) で落ちること・
   `GetVolumePathNameW` の入力の形（マウントしたフォルダを含む）・短いフォルダの下に長い子がある履歴の送り方・読み取り専用の属性で (a) が `BUSY` と取り違えないこと・
   中のファイルが開かれている履歴のディレクトリ・`FOF_WANTNUKEWARNING` を足すと「黙って完全に削除」が失敗に変わるか・呼び出し中にこのスレッドの窓へメッセージが配送されるか。
   測った結果が決定と食い違えば、実装の前にこの ADR を補正する。
3. **順は「md を確かめる → 履歴 → md」。**
   - 先に md について決定 2 の (a)〜(d) を済ませる。`BUSY` / `UNAVAILABLE` なら何も送らずに返す（いちばん起きやすい失敗 — 他のプログラムが md を開いている — は、ここで何も変えずに止まる）。
   - 履歴のディレクトリがあれば、決定 2 を通して 1 回目の呼び出しで送る。送れなければ md には触らずに返す。
   - md を 2 回目の呼び出しで送る。失敗したら `FAILED`（履歴だけがごみ箱に入った状態が残り得る。ノートは無事で、履歴はごみ箱から戻せる）。
   - **md が `ABSENT`（外で既に消えていた）でも、履歴があれば履歴は送る。** その上で `ABSENT` を返す（「ノートの無い履歴」を残さない）。
   2 回に分けるのは、項目ごとの成否を戻り値で知るため。1 回にまとめても原子的にはならない（実測）。
4. **port は 1 本: `trash_note(adapter, category, note) -> enum trash_outcome`。** 結果は閉じた列挙（専用ヘッダ・C-005）:
   `TRASHED`（履歴があれば履歴も）/ `ABSENT` / `UNAVAILABLE` / `BUSY` / `FAILED`。
   「1 つの対象を確かめて送る」部分は adapter の中の 1 関数にし、単位 C が孤立した履歴のカテゴリ `data/.history/<カテゴリ>/` を送るときに同じ関数を使う（ARC-001）。
   偽ポートにも同じ行を足す。
5. **application の意図 `folio_state_trash_note(state, struct note_ref target, units, count)`**（`units` / `count` は UI が持つ編集中の本文。改名と同じ受け方で 4 引数）:
   1. 対象が範囲外なら `NO_SUCH_CATEGORY` / `NO_SUCH_NOTE`。同期（ADR 0039 決定 5）。未完了の改名があれば既存の値で進まない。
   2. 対象が**開いている文書で編集中**なら、既存の保存を先に行う。失敗したらその値を返し、送らない。
   3. **確保を先に**: ノートを除いた台帳（`note_ledger_removed`）と、対象が開いている文書のときに要る空の表示値。
   4. `trash_note`。`UNAVAILABLE` / `BUSY` / `FAILED` は新しい結果の値（決定 6）で返し、状態は変えない。`ABSENT` は成功と同じに進む（照合が次回の起動でやることを今やるだけ）。
   5. `write_note_ledger`。書けなければ、初回保存と同じ「未同期の再試行」（`index_pending`）に載せて表示はファイルに従う（ADR 0039 決定 3）。
   6. 状態: `notes[]` の台帳を差し替え、`note_corpus` から落とし（core に削除を足す）、絞り込みの一致集合を作り直し、置換の下見と履歴の面を捨てる。
      - **対象が開いている文書なら、起動直後と同じ状態へ戻す**: 文書なし・**閲覧モード**・本文は空・**カーソル無し**（`cursor_any = false`）。次のノートは開かない
        （消した直後に別の md を読んで失敗する経路を作らない）。ノートのカーソルは選択そのものなので、「選ばずに次のノートへカーソルだけ置く」形は作らない。
        索引で `j` / `k` を打てば既存の規則で最初／最後の止まる行へ入る。
      - **「文書なし」での保存を断る**: `save_note` は無題に加えて文書なしも `NOTHING_SELECTED` で断る。文書なしのまま編集モードが残って、詰めた後の添字が指す
        別のノートへ本文を書く経路を作らない（単体で固定する）。
      - 対象が開いていないノートなら、選択・カーソル・保留の添字だけを付け替える。開いている本文・モード・Undo は変えない。
6. **足す結果の値は 3 つ**（文言は `ui_text` の 3 列・失敗の箱で出す。どれも「ノートは残っている」ことを言う）:
   - `FOLIO_STATE_TRASH_UNAVAILABLE`:「この場所ではごみ箱を使えないので、ごみ箱へ移していません。」
   - `FOLIO_STATE_TRASH_BUSY`:「ほかのプログラムが使っているので、ごみ箱へ移していません。」
   - `FOLIO_STATE_TRASH_FAILED`:「ごみ箱へ移せませんでした。」
   字面は実装の単位で整えてよいが、意味は変えない。
7. **UI**: `FOLIO_COMMAND_TRASH_NOTE`（「操作 ▾」・パレット・`:trashnote` / `:trash`）は開いている名前付きの文書を対象にし（無題・未選択は UI が `NOTHING_SELECTED`）、
   ノート行の右クリックメニューの「ごみ箱へ移す」は押した行を対象にする。成功して文書が無くなったときは、開いている面（履歴・置換・ノート内検索）を閉じ、本文を空にして
   フォーカスを索引へ返し、ドロワーと主窓を描き直す。呼び出しは UI スレッドで同期に行う（実測から 2 回で最大 0.7 秒ほど。進捗は出さない）。
   呼び出し中にメッセージが配送されると分かったら（決定 2 の未測定）、主窓は実行中の再入を断る。
8. **単位**: B1 = adapter の `trash_note`・shell32 の結線・adapter の実物を一緒にコンパイルした probe（決定 2 の未測定を含む）。
   B2 = `note_corpus` の削除・application の意図・「文書なし」の保存の拒否・結果の値 3 つと 4 か所の表・単体と確保失敗。B3 = コマンド・メニューの項目・文言・面の後始末。

## 強制

- shell32 が adapters 以外に結ばれないこと・ui が adapters を呼ばないことは ARC-002 / ARC-003 が **active**（OS ライブラリは CMake の `nenefolio_system_link` と
  `eng/architecture.json` で強制される）
- 意図の意味（保存が先・確保が先・`ABSENT` は成功・失敗は何も変えない・未同期の再試行・添字の付け替え・文書なしへ戻る・文書なしの保存を断る）は
  `tests/unit/state_tests.c` の偽アダプタ、`note_corpus` の削除と確保失敗は単体と `allocation_tests.c`（QLT-009）
- 決定 2 と 3（UNC で呼ばない・260 文字以上で呼ばない・開かれている md で何も送らない・履歴 → md の順・md が無くても履歴は送る）は、
  **adapter の実物を一緒にコンパイルした probe** を `D:\NeNeFolio\` の sandbox で動かして確かめ、確認記録に残す。単体テストは実物のごみ箱に触らない
- 結果の値 3 つの網羅は CNF-009、3 言語の列は CNF-011 が **active**

## 結果

得る: 消したノートと履歴がごみ箱から戻せる。ごみ箱を使えない場所・長いパス・リンクの先で黙って消える経路が無い。新しい OS ライブラリの許可は要らない。

失う・残る:

- **OS の設定でそのドライブのごみ箱を切ってある場合**（「ごみ箱にファイルを移動しないで、削除と同時にファイルを消去する」）は、`SHQueryRecycleBinW` が `S_OK` でも完全に消える見込み
  （未測定・推測）。利用者自身の OS の設定に従った結果として扱う。`FOF_WANTNUKEWARNING` で失敗に変えられると分かったら、決定 1 の旗を補正する
- ごみ箱の容量を超える大きさのファイルは完全に消える見込み（未測定。md と履歴は小さいので現実には起きにくい）
- 取り外しのできる媒体・ネットワークの場所では `UNAVAILABLE` になり、アプリの中からは消せない（エクスプローラで消して再起動すれば照合が拾う）。`SHQueryRecycleBinW` が
  それらで `S_OK` 以外を返すことは UNC と `subst` の根でしか測っていない
- 確かめてから呼ぶまでの間に、他のプログラムが md を開く・対象を入れ替えると、判定は古くなる。履歴だけがごみ箱に入って md が残る中途半端は、その窓でだけ起きる
- md をごみ箱から「元に戻す」で戻しても、履歴のフォルダは別の項目なので別に戻す必要がある。戻したものは再起動の照合で末尾に現れる
- 260 文字の制限で、深い場所に置いた `data/` の長い名前のノートは消せない（保存や改名は `\\?\` で通るので、この操作だけの制限になる）
- 呼び出しの間（最大 0.7 秒ほど）UI は止まる
- 開いている文書をごみ箱へ移すと、編集モードだった場合も閲覧モードへ戻る（文書が無いので）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| `IFileOperation`（`FOFX_RECYCLEONDELETE`） | 実測で「送れなければ失敗」にならない。ole32 の許可と COM の初期化だけが増える |
| 判定せずに呼び、戻り値を信じる | UNC・`subst`・長いパスで戻り値 0 のまま完全に消える（実測） |
| `compose` のパスの文字列だけで判定する | 親がリンクや `subst` だと実体の場所が分からない。開いたハンドルの実体のパスで判定する |
| 呼んだ後でごみ箱の件数の差を見る | 消えた後では戻せない。他のプログラムの出し入れと区別できない |
| md と履歴を 1 回の呼び出しで送る | 原子的にならず（2 つ目が開かれていると 1 つ目だけ消える）、どちらが失敗したか分からない |
| md → 履歴 の順 | 止まると「ノートの無い履歴」が残り、同じ名前のノートを作り直すと付いて来る |
| 送れない場所では確認して完全に消す | 分岐する箱を作らない（ADR 0038）。裁定は「ごみ箱へ」 |
| 消した後に次のノートを開く／次のノートへカーソルだけ置く | 前者は別の md の読み込みの失敗を消す操作の結果に混ぜる。後者はカーソルが選択そのものである今の型で表せない |
| 編集中の本文を保存せずに送る／UI が先に保存してから意図を呼ぶ | 前者はごみ箱の md が古くなる。後者は「保存が先」を UI の記憶に頼ることになる |

## 2026-10-08 の補正（#195）— 完全削除へ進まない専用 API

設計サナが実物のソース・ログと Microsoft の仕様を照合し、実装の前に受理した。hide の「ごみ箱へ」の裁定と、決定 3〜6 の port・順序・状態遷移は維持する。

### 根拠

- 前回の追加実測（`D:\NeNeFolio\design\2026-10-07\trash-probe-2\`）では、短い履歴フォルダでも長い子があると、
  `SHFileOperationW` は戻り値 0 のままフォルダごと完全削除した。`SHQueryRecycleBinW` は件数とサイズの照会で、次の削除先を保証しない。
  固定の葉名 `\1.md.tmp` の長さだけを足す初版の事前判定では、外から加わった長い子を守れない。
- `IFileOperation` に削除直前の sink を付けると、通常 3 場面はごみ箱へ移り、取消 5 場面（subst・UNC・長いファイル・長い子・常時取消の対照）は元を保持した
  （`D:\NeNeFolio\design\2026-10-08\trash-callback-probe\report.md`）。ただし固定の COM callback は最大 8 引数で C-012 の例外が必要になる。
- **専用の `ITransferSource::RecycleItem` は sink を要さない。** 短いファイル、子 2 つのフォルダ、340 文字の子を含む短いフォルダで
  `COPYENGINE_S_DONT_PROCESS_CHILDREN` と移動後の Shell item を返した。元は無く、ごみ箱の項目と全ての子の本文を確認した。
  326 文字のファイルは `COPYENGINE_E_RECYCLE_PATH_TOO_LONG`、UNC は `COPYENGINE_E_RECYCLE_BIN_NOT_FOUND` で、元を残して返った
  （`D:\NeNeFolio\design\2026-10-08\recycleitem-probe\report.md`）。
- 長いパスの拒否・長い子の成功・UNC の拒否では呼び出し中の隠し窓への WM_APP とタイマー配送は各 0 回だった。Windows 全版で再入しないという保証にはしない。

### 決定 1・2 の置換

1. **呼ぶのは `ITransferSource::RecycleItem` だけ。** 元の Shell item の親から `BHID_Transfer` / `IID_ITransferSource` を得て、
   `FOLDERID_RecycleBinFolder` の Shell item を宛先に `TSF_NORMAL` で呼ぶ。
   `SHFileOperationW`・`IFileOperation::DeleteItem`・`ITransferSource::RemoveItem` へのフォールバックは置かない。
   ごみ箱を使えない設定・場所の拒否を、通常削除へ読み替えない。
2. **adapter は錠を持ち、未完了の改名記録が無いと確かめてから進む。** 錠なし・記録あり・記録の有無を読めない場合は `FAILED`。
   `data/` を作る・錠を横取りする経路は足さない。application は既存の同期を先に行う。
3. **対象の事前確認を残す。** md はファイル、履歴はディレクトリでなければ `UNAVAILABLE`。対象自体を
   `DELETE | FILE_READ_ATTRIBUTES`・共有なし・`FILE_FLAG_OPEN_REPARSE_POINT`（ディレクトリでは `BACKUP_SEMANTICS` も）で開き、
   name surrogate を拒む。開けない理由が共有違反なら `BUSY`、ファイル/パス不在なら `ABSENT`、それ以外は `FAILED`。
   ハンドルの実体パスを取得し、UNC・ローカル NTFS 以外・対象パス自体が 260 文字以上・照会不能を `UNAVAILABLE` にする。
   `\\?\` を外した実体の絶対パスだけを Shell へ渡す。subst や親のリンクは実体へ解く。
4. **履歴の子を推測の固定長では検査しない。** 専用 API にディレクトリの移動だけを依頼し、移せない場合に子を完全削除する処理を呼ばない。
   長い子の内容保持は上記で測った。トップレベルのパス長制限は初版の保守的な境界として残す。
5. **成功は `SUCCEEDED(hr)` だけでは決めない。** 移動 API が成功し、移動後の Shell item を返したときだけ `TRASHED`。
   `COPYENGINE_S_NOT_HANDLED` などの処理していない結果や移動後項目なしは成功にせず、元を残して拒否する。
   明示的なごみ箱非対応の HRESULT は `UNAVAILABLE`、それ以外の失敗は `FAILED`。先の open で確かめた共有違反だけを `BUSY` と呼ぶ。
6. **COM は adapter に閉じる。** 呼び出し中に STA を初期化し、`S_OK` / `S_FALSE` で成功した分だけ、参照を解放した後に `CoUninitialize` する。
   既存の異なる apartment は `UNAVAILABLE`。自作の COM sink、callback、背景スレッドは足さない。
   shell32・ole32・uuid（Windows SDK の GUID 定義）を adapters の `nenefolio_system_link` で結ぶ。
   ole32 / uuid を `platformLibraries.adapters_win32` に追加する。実行時の第三者依存は増えない。
7. **md 事前確認 → 履歴 → md の順は変えない。** md が事前確認で拒否されたら履歴も動かさない。
   md 不在でも残った履歴を送り、その後 `ABSENT` を返す。履歴が移った後で md の移動が失敗する可能性は残り、履歴はごみ箱から別に戻せる。
   「1 対象を確かめて送る」経路を adapter の中で 1 本にし、単位 C もそれを使う。準備完了を `TRASHED` と名付けない。

### 決定 7・8、結果と限界

- UI スレッドの同期呼び出しは維持する。旧 API の「最大 0.7 秒」は新 API の上限ではない。
  本体を呼び出し中に別の変更意図が入る場合は重ねて実行しない。B1 の実 adapter probe で配送を記録し、B3 が UI の境界を確認する。
- B1 はこの契約の port・adapter・既存偽 port への結線と、**製品 adapter の実物**を使った隔離 probe を含む。
  B2 / B3 の分け方は維持する。初版の一般削除 API と新 API を並行して製品へ持ち込まない。
- OS 設定を変える実測（ごみ箱無効・容量超過）と他の Windows 版は未実施。
  専用 API の契約に従い、ごみ箱移動以外の API を呼ばないことを構造上の防護とする。実測していない条件を「測定済み」とはしない。
- 事前確認のハンドルを閉じてから Shell が対象を開くまでの入れ替わり、2 対象の非原子性、別々の復元、トップレベルの長いパスの拒否は残る。
  初版の「OS 設定による完全削除は利用者の設定に従った結果として扱う」は撤回する。
- C-012 の引数数に例外を設けない。sink 案は実測成立したが、専用 API で同じ目的をより少ない OS 境界で実現できるため採用しない。
