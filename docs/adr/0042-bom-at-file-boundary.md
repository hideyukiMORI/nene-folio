# ADR 0042 — BOM はファイル境界で一度だけ解釈し、本文の U+FEFF は保持する

- 状態: 受理
- 日付: 2026-10-12
- Issue: #271
- 影響する規則: ARC-001 / ARC-004 / ARC-007 / ARC-008 / ARC-009 / ARC-010 / C-003 / C-005 / C-007 / C-008 / C-014 / C-016 / QLT-008 / QLT-009 / QLT-013

## 文脈

main `2f4f334`（製品 `130bfda`）の実 Win32 probe で、先頭 U+FEFF の多重除去を確認した。
`file_bytes_read` と `note_text_create` がそれぞれ BOM を 1 個除き、`note_text_from_editor` がさらに 1 個除く。
本文の複製も `note_text_create` を呼び、履歴は `file_bytes` が BOM を除いたあとの bytes を保存していた。

`U+FEFF × 3 + A` のファイルは、読み込み・編集表示では `U+FEFF + A`、何も打たない保存で `A` となった。
RichEdit の変更印は 0 だが application は CHANGED と判定し、履歴を 1 版作って書き換える。
`U+FEFF × 1 + A` は本文 `A` として読み、未編集保存では元のファイルを保持した。
証跡は `D:/NeNeFolio/agents/2026-10-12-text-boundary/`（#270）。

[Unicode の説明](https://unicode.org/faq/utf_bom.html)は、ストリーム先頭の署名と、本文中の U+FEFF を区別している。
先頭の署名を取り除いた本文を再び「ファイル入力」と解釈すると、本文を複製するだけでも文字が減る。
全ての先頭 U+FEFF を捨てる正規化ではなく、入力・本文・出力の境界を区別する必要がある。

## 決定

この ADR は [ADR 0004](0004-first-drawer-slice.md) のファイル読取時のBOM除去位置、
[ADR 0006](0006-edit-mode-and-save-path.md) 決定 3 の BOM の扱いと、#227 の保存上限の計数を補正する。
通常のノートは BOM を付けずに保存する。**本文先頭の U+FEFF を再読込で署名と誤認させないために必要な場合だけ、署名を 1 個付ける。**
原文の BOM の有無を状態として覚えることはしない。出力の署名は現在の本文だけから決まる。

1. **ファイルの bytes は解釈しない。** `file_bytes` の所有バッファと公開 getters は読み取った全 bytes を返す。
   保存・新規作成は渡された全 bytes を書く。`archive_note` は保存直前のファイルを BOM 込みでそのまま履歴へ写す。
   ロック・一時ファイル・公開・履歴の回転と失敗の順序は変えない。
2. **署名を識別する実装は core の 1 か所。** `utf8_text_bom_length(bytes, length)` が先頭の UTF-8 BOM の長さ（0 または 3）を返す。
   `note_text_create` はファイル入力として署名を 1 個だけ消費し、残りを本文として検証・所有する。
   `json_reader_create` も入力先頭の署名を 1 個だけ消費する。ファイル経由の JSON の受理範囲は維持し、core の parser 直呼びも
   署名 1 個を受理するようになる。署名 2 個は既存の文法解析で不正となり、文字列内の U+FEFF は保持する。
3. **本文は再びファイルとして解釈しない。** `note_text_from_editor` は入力の U+FEFF を削らず、既存の UTF-8 検証・NUL 拒否と
   CR/LF/CRLF の正規化を行う。`note_text_copy` は検証済み本文を内部の所有処理 `adopt` で複製する。
   閲覧中の別名保存と `note_corpus_put` はこのコピーを使い、ファイル入力用の `note_text_create` を通さない。
4. **本文と保存表現は同じ所有バッファから借りる。** `note_text` の所有処理は、本文が U+FEFF で始まる場合だけ
   その直前へ署名 3 bytes を置く。既存の `note_text_bytes` / `note_text_length` は本文だけを返す。
   `note_text_file_bytes` / `note_text_file_length` は署名を含む保存表現を返す。状態の所有者と確保の回数は増やさない。
   adapter の `write_note` / `create_note` は両方とも保存表現を使う。UI・RTF・検索・本文比較は本文を使い続ける。
5. **16 MiB は保存表現の上限。** 必要な署名 3 bytes を含め、保存できる `note_text` しか生成しない。
   `note_text_create` と `note_text_from_editor` は確保前に確認し、超過なら既存の `NOTE_TEXT_TOO_LARGE` を返す。
   不正 UTF-8 → 埋め込み NUL → 上限超過の優先順は維持する。拒否時の out と既存本文は不変。
   入力ファイル自体の上限も `file_bytes` の既存 16 MiB を維持する。
   通常本文と、保存すると消える単独の署名の扱いは変えない。
6. **同じ本文なら保存しない。** 署名を 1 個取り除いた本文と編集後本文が同じなら、元ファイルの bytes と履歴を変えない。
   原文の署名の有無だけを理由に保存しない。履歴から読むときも通常ノートと同じファイル入力を通り、復元する本文には署名を混ぜない。

## 検証と強制

- 中核の対象テストで、署名 0/1/2/3/4 個、途中・改行後の U+FEFF、コピー、編集入力、保存表現、上限前後と out 不変を固定する。
- JSON の共通読取と代表の台帳・設定・改名記録について、署名 1 個の受理と 2 個の拒否を確認する。
- application は未編集の no-write/no-history、実編集と別名保存、検索写し、履歴読取/復元を確認する。
- 実 Win32 の代表ケースで、RichEdit からの取得、実保存・再読込・履歴 raw の一致を確認する。
- 確保失敗は既存の測定ビルドで確認する。ゲートの閾値・除外・重大度・依存を変えない。
- `eng/check.ps1` の成功だけで全 OS の表示や IME を確認したとはしない（QLT-013）。

## 結果

ファイル入力の解釈は各形式の入口だけになり、本文のコピーや編集の保存で文字が減らなくなる。
本文先頭が U+FEFF のときは保存表現が 3 bytes 長くなり、本文として使える上限もその分だけ短くなる。
これは新しい独自形式ではなく UTF-8 の署名である。JSON schema の版、通常ノートの出力、履歴の配置と保持数は変わらない。
過去の処理で失われた文字は自動復旧できない。履歴の raw 保持は修正後に作る履歴からの保証である。
既存ファイルの一括変換は行わない。Waivers: none。

## 却下した選択肢

| 選択肢 | 理由 |
| --- | --- |
| 先頭の U+FEFF を全て削る | 本文の文字を削除して正規化を冪等にするため、保持の要件を満たさない |
| RichEdit の変更印だけで保存を省略する | 本文比較とは別の事実を application に持ち、実編集後の文字欠落も防げない |
| 先頭 U+FEFF を含むノートの編集を拒否する | RichEdit 自体は保持でき、原因は自前の入出力の多重解釈。コピー・履歴の欠落も直らない |
| 全ての保存で BOM を付ける | 通常ノートの出力まで変える必要がない |
| 読んだ BOM の有無を永続的に覚える | 本文保持に必要な出力は本文から導けるため、独立した状態は不要 |
| file_bytes に raw/text の二つの読み方を作る | 同じファイル読取を二つに分けず、ファイルは bytes、形式の入口は解釈という責務で分けられる |
