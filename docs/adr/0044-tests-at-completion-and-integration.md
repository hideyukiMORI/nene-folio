# ADR 0044 — 有意味な対象テストを機能完成時、フルゲートを統合時へ集約する

- 状態: 受理（2026-10-12のhide指示を具体化。設計: AstraのNeNeFolioサナ）
- 日付: 2026-10-12
- Issue: #280
- 影響する規則: QLT-001 / QLT-005 / QLT-008 / QLT-010 / QLT-012 / QLT-013 / GIT-004
- 関連: [ADR0037](0037-required-check-verdict.md)の必須CIを維持し、[ADR0043](0043-current-instructions-and-single-agent.md)決定5の検証頻度を具体化する。Ready直前のローカルフルゲート義務を本決定で改める。他の運用判断は変更しない。

## 文脈

hideは「意味の薄いテストが多すぎる」と指摘し、一区切りの機能が完成した時やマージ時に有意味な検証をまとめ、時間を節約する方針を求めた。
確認基点はmain `8f2399c`。ワークフロー§2と入口はReady直前のローカルフルゲートを要求し、その後に同じ `eng/check.ps1` をCIでも実行する。
QLT-012の「反復中は最も狭い検査」だけでは、細かな編集ごとに走らせる必要がないことが伝わらない。
直近の#271では対象unit、ローカルフルゲート、実OS、CIを実施し、#274/#276/#278の文書変更では製品の成功済み結果を再利用した。
個々の過去のテストを無意味と断定するものではなく、今後の実行理由と時点を明確にする。

`.githooks/commit-msg`にフルゲート起動は無く、`tools/merge-pr.ps1`もReady化とCI待ちを行うだけである。
CIは非Draftの `edited` でも再起動するため、Ready後の本文更新だけで同一headのフルゲートを繰り返し得る。
既存の機械経路を変えず、運用の集約でこの重複を減らせる。

## 決定

**受け入れ条件を確認する対象テストを機能単位の完成時にまとめ、統合のフルゲートは最終PR headの必須CIで通す。**

1. 着手時に、変更する利用者の振る舞い・守る契約・直接影響する境界と、その受け入れ条件を短く決める。
   各テストは、どの具体的な誤動作を検出するか説明できるものにする。既存のテストで条件を満たすなら重複して追加しない。
   実装の行をなぞるだけのassertion、件数の水増し、同じ保証の別席による再測定を目的にしない。
   既存テストの一括削除は行わず、整理が必要ならそのテストが守る契約を調べた焦点Issueで扱う。
2. 編集中は一行・一ファイル・一commitごとにテストを起動しない。一区切りの機能を実装し、自己レビューで候補を整えた時に、
   変更機能と直接影響する境界の対象テストを一度まとめて実行する。完成とは受け入れ条件を確認できる候補が揃った状態を指す。
   回帰不具合の修正前red、コンパイル不能、原因を切り分けないと実装判断ができない場合は、途中でも必要な最小の再現・診断を実行できる。
   その理由と結果を残し、診断を理由に無関係な全件検証へ広げない。
3. 成功済み結果には対象commitまたは入力の識別、コマンド・結果・対象範囲・必要な環境条件・証跡を残す。
   関係する実装・テスト入力・依存・ビルド設定・環境条件が不変なら、受け渡し・レビュー・commit・push・mergeだけで対象テストを再実行しない。
   関係入力の変更、失敗、または具体的な未解決の疑いがあれば、その影響範囲を再検証する。
   文書しか変わっていないことは差分で確認し、SHAが変わったという理由だけで製品検証をやり直さない。
4. PRは実装・レビュー中Draftのままにし、head・タイトル・本文を確定してから一度Readyにする。
   統合時には最終headでCIの `pwsh -NoProfile -File ./eng/check.ps1` と必須 `check` が成功していることを要求する。
   **同じフルゲートのローカル先行実行は一律必須としない。** 共通基盤の問題の診断やCI失敗の再現など、具体的な理由がある場合だけ実行する。
   Ready後にheadを変える必要があれば先にDraftへ戻し、修正と必要な対象検証をまとめてから再びReadyにする。
   CI実行後の結果はCIと外部証跡に残し、結果をPR本文へ追記するためだけの `edited` 再起動を避ける。
   失敗・取消・未起動を成功と扱わず、原因を確認してから必要な再実行を行う。古いSHAの成功や対象テストは最終CIの代わりにならない。
5. 文書・コメント・運用規則だけの変更では、ローカルは差分・参照・関係する規約検査で完結させる。
   ツール変更ではそのツールの動作を確認する。製品の実機検証は、その変更が触れたOS境界や表示条件を対象テストで保証できないときだけ行う。
   全件回帰・大規模matrixは、共有基盤などへの具体的な影響と狭い確認で不足する理由を説明できる場合に限る。
   現行の必須CIは文書PRでもフルゲートを実行する。本決定ではCIの除外や別の完了経路を作らない。
6. ゲートの検査内容・重大度・90%下限・除外・必須check・strict・統合ツールを変更しない。
   無関係な既存テストの失敗は分離して記録し、全件再試行や別件修正を勝手に追加しない。必須CIの失敗が残れば統合は保留する。
   機能の実装・対象検証が済んだ段階と、必須CI・統合・必要反映まで済んだ完了を区別して報告する。

## 強制

- 最終headの必須CI成功: **active**。ADR0037の `full-gate` / `check` と既存rulesetをそのまま使用する。
- 対象テストの有意味性・実行時点・再利用の妥当性: **不能**（判断）。QLT-008/012、ワークフロー、委任指示書で記録・レビューする。新たな機械強制を主張しない。
- 文書の意味と参照を確認し、`eng/conformance.py`で既存の規約整合を検査する。最終headの必須CIを通して統合する。
  ローカルの実行頻度だけの変更であり、製品・検査器・CIに移行するコードや新たなnegative proofは無い。

## 結果

通常の機能変更では、完成時の対象検証と統合時の必須CIに実行を集約できる。担当交代やPR本文の追記による重複も減らす。
ローカルフルゲートでしか先に見えなかった問題は、CIで初めて見つかる場合がある。その場合は失敗範囲を診断してから修正する。
短縮時間は未測定。CIの成功はテストの意味、物理IME、未測定のDPI/OS、hideの目視結果まで証明しない。
今回の変更は運用文書のみであり、成功済みの製品検証と通常exeを再実行・再ビルドしない。

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 編集のたびに狭いテスト、Ready前とCIで同じフルゲートを必ず実行する | 実行時点の重複が残り、今回の時間節約の依頼に応えない |
| 原因調査の最小再現まで全てマージ時へ遅らせる | 不具合や設計上の不確実性を切り分けられず、手戻りを増やす |
| 閾値を下げる、既存テストをまとめて削る、文書PRの必須CIを飛ばす | 保証の欠落や別経路を生み、実行頻度の整理を超える |
| ローカルの古い成功を最終headのCIの代わりにする | 未検証headを統合でき、ADR0037の保証を損なう |
