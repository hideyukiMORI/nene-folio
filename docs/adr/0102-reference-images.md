# ADR 0102: 画像の参照形式は定義の行を既存の画像の経路へ渡す

Status: accepted / 2026-11-17 / Issue #863

[ADR0101](0101-reference-links.md)の「画像の参照形式は解かず、原文のまま」だけを置き換える。定義の表・読む規則・リンクの扱いは変えない。

## 背景

ADR0101では、画像の読込経路（`markdown_media_image` → `markdown_images_append`）が「いま描いているviewの範囲」を前提にするので、画像の参照形式を別Issueにした。
調べると、この経路が使うのはviewのspanが指す原文のbytesの位置（`span->bytes - source`）だけで、spanが同じノートの原文を指していれば、どの行のviewでもよい。

## 決定

- 定義の表は、各定義の行の開始位置・長さと、行の中の行先の範囲を持つ。原文のbytesは描画の間だけ借りる。
- 行内で画像の印の付いた括弧の対が完全・省略・短縮の形で定義を引けたら、定義の行を1つのspanとするviewと行先の範囲を、そのまま`markdown_media_image`へ渡す。
  相対pathの解決・原文の位置の記録・遅延読込・上限・書出し（ZIP）での行先の書き換えは、丸括弧の行先の画像と同じ経路で行われる。
- 書出しの行先の書き換え（`markdown_image_copy_create`）は、受け取った位置を原文の順に並べ、同じ位置の重複を1つにする。
  同じ定義を参照する画像は同じ位置を持ち、行内の画像は参照の画像より先に集まるので、集めた順は原文の順と限らない。同じ位置を別の行先へ書き換える指示は拒む。
- 説明（alt）は1つ目の括弧の中。読めない画像は丸括弧の形と同じく原文の文字のまま（`![説明][ラベル]`）。見つからないラベルも原文のまま。

## 却下した案

- 書出しの側で重複と順序を避ける: 集める側（描画）と書き換える側の両方に順序の約束が散る。書き換える側が入力の順に依らない形にした。

- 表の行先（展開済みのbytes）から画像を作る第2の経路: 原文の位置が無くなり、書出しで行先を書き換えられない（ARC-001）。

## 検証

3つの形の画像参照が画像になり、記録された範囲が定義の行先の原文を指し、行先が1回だけ展開されること、見つからないラベル、同じ定義へのリンクの参照を単体で、
nativeの画像の枠として入ることと定義が表示されないことをnativeで確かめる。Waivers none。
