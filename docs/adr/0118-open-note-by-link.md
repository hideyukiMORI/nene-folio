# ADR 0118: 指定したノートを開いて箇所を選ぶ入口（`nenefolio://`のリンク）

Status: accepted / 2026-11-20 / Issue #1071（hideの判断: 2026-11-20、[判断のページ](https://claude.ai/artifact/MKr49ZHc4sRPPLAifGd1xA)の5点は「ぜんぶ推し」。実装した段階をこの文書に書き足す）

## 背景

LLM（WSLのClaude Codeなど）がノートを探して説明するとき、該当のノートを開いて、読んでほしい箇所を選んだ状態で見せたい（#1071、2026-11-13の検討の3）。
hideは2026-11-19に、SPECIFICATIONの「やらないこと」を改めて、これを取り入れると決めた。進める順は #1069 → このリンク → #1070と依頼のファイル → #1062。

前提と縛り:
- WSL側のLLMは、Windows側の実行ファイルを起動しない。LLMが答えにリンクを書き、利用者がクリックする。
- 読み取りだけ。書き込みの口は開けない。ローカルのポートで受けるHTTPのAPIは採らない（#1071の「採らないもの」）。
- いまのアプリは引数を読まない（`wWinMain`が`arguments`を捨てている）。同じ`data/`を使う2つ目の起動は、`data/.nenefolio.lock`で断られ、箱を出して終わる（ADR0022の決定3）。
- 外から来た値は、最初の自前の境界で検証して型へ変える（ARC-008）。プロセスの状態を読んでよいのは`adapters/win32`と入口だけ（ARC-007）。

この文書はリンクを決める。依頼のファイル（`data/.requests/`）は#1070のフォルダの見張りと一緒に、次のADRで決める。箇所の探し方と開く経路は、依頼のファイルでも同じものを使う。

## 決定

1. **リンクの形**: `nenefolio://open?category=<カテゴリ名>&note=<ノート名>&lines=<始>-<終>&text=<探す文>`。
   - `category`と`note`は必須。`lines`と`text`は任意。`lines`は原文（Markdownのファイル）の1始まりの行で、`3-8`または`3`。
   - 値は%で符号化したUTF-8。キーは小文字で、大小を区別する。知らないキーは値を読まずに無視する（後で足せるように）。知っているキーが2回あれば不正。
   - `open`以外の動作は不正として断る。書き込み・作成・削除の動作は作らない。
   - 全体の長さの上限はUTF-8で2,048byte（コマンドラインとShellの上限より内側）。`text`は復号後1,024byteまで。値に制御文字（C0・DEL・C1）と行・段落の区切り（U+2028・U+2029）は置けない。
2. **検証は中核の1か所**: 新しい中核の型`open_request`（`src/core/open_request.h`）が、文字列から作られる唯一の入口を持つ。
   - スキームと動作の確かめ、queryの分解、%の復号、UTF-8の確かめ、`category_name`・`note_name`への変換（既存の名前の規則＝区切り文字・予約名・長さをそのまま使う）、`lines`の範囲の確かめを行う。
   - 結果は閉じた`enum`（受理／形が不正／名前が不正／長すぎる／記憶不足）。受理した値だけがapplicationへ渡る。
   - ノート名に`.md`が付いていれば落とす（既存の`note_name`の振る舞い）。
3. **開く経路は既存の1本**: 窓の`switch_note`（ノートを切り替える唯一の経路、ADR0013の決定4）を通す。新しい経路は作らない（ARC-001）。
   - 編集中の名前のあるノートは、ドロワーのクリックと同じく黙って保存してから移る。保存に失敗したら移らない。
   - 無題の下書きがあれば、ドロワーのクリックと同じく名前の入力を出す。取り消したら開かない。
   - 流し込み中・削除中・面（設定・名前の入力など）を開いている間は、開かずに1行で知らせる（面を閉じて開く、はしない。入力の途中のものを勝手に閉じない＝hideの判断2）。
   - カテゴリ名とノート名は、applicationがいまの一覧から位置を引く（大文字小文字は区別しない＝Windowsのファイル名と同じ）。見つからなければ開かずに知らせる。一覧に無いノートを作らない。
     引く前に、カテゴリの台帳と、そのカテゴリのノートの台帳を読み直す（[ADR0117](0117-refresh-ledgers-before-write.md)の部品。読み直しても書かない）。依頼を書いた側（LLMなど）が、直前にノートを外で作っていることがあるため。
   - 絞り込み中・「お気に入りだけ」の表示でも開く（一覧の見え方は変えない。開いたノートは右の窓に出る）。カテゴリが閉じていれば開く（利用者の作った絞り込みを、外から来たリンクで壊さない＝hideの判断3）。
4. **箇所の探し方**（#1071のとおり。依頼のファイルと共通）: `lines`のあたりで`text`を探す → 無ければノート全体から探す → 無ければ`lines`を選ぶ → どれも無ければ開くだけ。
   - 「あたり」は`lines`の範囲の前後5行まで。
   - `text`は原文の上で、大文字小文字を区別して探す（LLMは原文を読んで引用するため）。最初の一致を選ぶ。
   - 探すのは保存済みの原文。中核の純粋な関数（原文・行の範囲・探す文 → 原文の範囲または「無い」）にして、単体の試験で固める。
5. **見せ方**: 閲覧表示のまま、該当の箇所を選んで見える所へ送る。編集表示にはしない（読み取りの入口。利用者が編集中だった場合も、保存の後は閲覧で見せる＝hideの判断1。編集表示のまま選ぶ案は採らない）。
   - 原文の範囲から閲覧の範囲へは、ADR0116の対応表（`markdown_source_map`）を逆に引く（原文の範囲に重なる段落の、最初から最後まで）。段落より細かくは選ばない（閲覧表示は原文と文字が1対1でないため）。
   - 対応表が引けない段落（図・表の一部など）は、その段落全体を選ぶ。
   - 見つからなかったとき・`lines`へ落ちたときは、1行で知らせる（「指定の文は見つかりませんでした。行を選んでいます」など。文はUX copyで決める）。
6. **動いているアプリへ渡す**: 2つ目の起動は、リンクの引数があり、かつ`data/`が使用中なら、箱を出さずに、動いている窓へリンクの文字列を渡して終わる。
   - 相手は、主窓のclass（`NeNeFolioWindow`）の窓のうち、同じ`data/`を持つもの。`WM_COPYDATA`で「dataの場所＋リンクの文字列」を送り、受け手は場所が自分のものと同じときだけ受ける（ZIP版を2か所に置いて同時に使っている場合に取り違えない）。
   - 受け手は、送り手を信用しない。受けた文字列を、起動の引数と同じ`open_request`の入口でもう一度検証する（ARC-008。同じ利用者のどのプロセスも`WM_COPYDATA`を送れる）。
   - 送る前に、送り手が`AllowSetForegroundWindow`で受け手に前面へ出る権利を渡す。受け手は最小化を戻して前面へ出る。
   - 動いているアプリが無ければ、ふつうに起動してから開く（窓ができて最初の描画の後）。
   - 渡せなかった（窓が見つからない・応えない）ときは、いままでどおり「使用中」の箱を出す。
7. **登録**
   - MSIX版（Store）: マニフェストに`uap:Protocol Name="nenefolio"`を足す（`eng/release.py`の`msix_manifest()`と`eng/test-release.py`）。
     起動したプロセスへURIがどう届くか（コマンドラインか、WinRTの`GetActivatedEventArgs`だけか）は、Microsoftの文書からは確かめられなかった（調べた記録: D:/NeNeFolio/agents/open-link-1071/research-20261120.md）。
     **実機で確かめるまで、マニフェストは変えない。** 先にアプリの側（引数で受けて開く・動いているアプリへ渡す）を完成させ、登録の1行は、hideが戻ってから一緒に実機で確かめて入れる（hideの判断5）。確かめるにはパッケージの登録が要り、hideの端末のStore版と同じ身元なので、留守中には触らない。
   - ZIP版: アプリはレジストリに書かない（置くだけで動き、消すだけで消える、を保つ＝hideの判断4。設定から登録する案は採らない。要望が出たら別のADR）。
     ZIP版でも、引数にリンクを渡せば開く（`NeNeFolio.exe "nenefolio://open?…"`）。LLMからは、#1070の依頼のファイルが主な道になる。
8. **層**
   - `core`: `open_request`（検証と型）、箇所を探す純粋な関数、対応表の逆引き。
   - `application`: 名前から位置を引く、保存済みの原文から箇所を決める、結果の閉じた値（開いた／カテゴリが無い／ノートが無い／文が見つからず行を選んだ／開いただけ）。
   - `ui/win32`: `switch_note`を通して開き、選んで送り、1行を出す。`WM_COPYDATA`の受け口。
   - `app`（入口）: 引数を読む、`data/`が使用中のときに渡す。引数を読むのはここだけ。
9. **やらないこと**: 書き込みの動作、HTTPのAPI、開いたことの外への通知（既読の報告など）、リンクからの新しいノートの作成、複数の箇所の同時の強調。

## 理由

- リンクは利用者のクリックを通るので、LLMが勝手に画面を動かさない。開くだけ・選ぶだけなので、悪意のあるリンクでできることは「一覧にあるノートを開く」に限られる（名前の規則でdataの外は指せない）。
- 既存の「ノートを切り替える唯一の経路」を通すことで、未保存の編集と無題の下書きの扱いが、クリックと同じになる（新しい失い方を作らない）。
- 2つ目の起動から1つ目へ渡す道が無いと、アプリを開いたままリンクをクリックするたびに「使用中」の箱が出る。これがこの機能の主な使い方なので、渡す道は最初から要る。

## 実装の状態

- 段取りの2と3の中核とapplicationは実装済み（#1095: `open_request`・`open_place`・`folio_state_locate_open_request`・`folio_state_open_place`と単体の試験）。まだどこからも呼ばれない（入口と窓は次の段）。
  - 実装で決めたこと: キーの振り分けは、キーの表と受け取り手の表の組で行う（番号の決め打ちにしない）。名前はASCIIの英字だけ大小を問わずに引く（ASCII以外の大小と正規化の違いは別の名前として扱い、「見つからない」側へ倒す）。
  - 窓の段への約束（独立レビューの指摘。#1069の教訓と同じ）: 位置を引く意図は、どの結果でも一覧を読み直した新しいものにしうる。番号を持つ面が開いているあいだは呼ばない。編集中の保存や無題の下書きの名前付けは、引く**前**に済ませる（依頼は名前で持ち、番号は引いてすぐ使う）。呼んだ後は結果によらず描き直す。
  - 行の指定が空の行だけのとき、範囲は長さ0になる。窓の段は、その行にキャレットを置く形で扱う。
- 窓と入口は実装済み（#1097）。**リンクをクリックして開くための登録（決定7）だけが残っている**。いま使える道は、引数にリンクを渡す起動（`NeNeFolio.exe "nenefolio://open?…"`）。
  - 窓: `folio_window_open_link`が、起動の引数と、動いている窓へ渡された依頼の共通の入口。**ここではリンクを写して預かり、自分へ知らせるだけ**で、開くのはメッセージの待ちの先頭（`folio_message_open_link`）。
    受けた所（`WM_COPYDATA`の中）で開くと、名前の入力や失敗の箱が出たときに送り手が5秒で諦め、2つ目の起動が「使用中」や場所の選び直しまで進んでしまう（独立レビューが見つけた）。預かれるのは1つで、開く前に次が来たら新しいほうに替わる。
    開く手順: 検証（`open_request`）→ 面や操作の途中なら断る → 位置を引く（一覧を読み直すので、結果によらずドロワーを描き直す）→ `switch_note`で開く → 編集表示なら保存して閲覧へ → 本文の区画を出す → 箇所を選ぶ。
  - もう開いているノートでも、閲覧表示なら読み直す（リンクを書いた側が、直前にファイルを書き換えていることがある）。同じノートを編集中なら、その編集を捨てずに、ふつうの保存をしてから閲覧で見せる（外の変更とぶつかったときは、保存が止まり、リンクのノートは開かない。ADR0119の決定4 / FR-059）。
  - 断る条件（決定3）: ノート内検索以外の面が開いている、OSのダイアログ、削除の途中、終了の途中、表示の切り替えの途中、本文の流し込み中、ポインタをつかんだドラッグの途中、日本語入力の変換の途中、ほかの処理の入れ子の中、窓が無効。
    OSのダイアログが出ているあいだは、窓を前面へ出すこともしない（ダイアログから入力を奪わない）。面が開いているあいだの「ほかの操作の途中」の1行は、面を閉じると消える。
  - 箇所: 原文の範囲から閲覧の段落へは、対応表を逆に引く（`markdown_source_lookup_paragraphs`。重なるブロックを閲覧の順で最初から連続して取る。空行だけの範囲は次のブロック）。閲覧欄では段落の記号（CRとU+0007）を数えて選び、選択の始まりが見えるように送る（`note_pane_select_paragraphs`）。
  - 知らせ（右の窓の下端の1行。文は D:/NeNeFolio/agents/open-link-1071/ux-copy-20261120.md で決めた）: 形が正しくない／ほかの操作の途中／カテゴリが無い／ノートが無い／文が無く行を選んだ／文が行の近くに無く別の場所を選んだ／箇所が見つからない。行のあたりで文が見つかったとき（ふつうの成功）は何も出さない。
  - 受け渡し: `WM_COPYDATA`（`folio_open_link.h`。dwDataは決めた値、lpDataはUTF-8の「dataの場所・NUL・リンク」）。受け手は場所が自分のdataと同じときだけ受け、リンクは起動の引数と同じ検証を通す。送り手（`folio_launch_link_hand_over`）は主窓のclassの窓を順に当たり、応えない窓は5秒で飛ばす。
  - 入口: 引数が`nenefolio:`で始まるときだけリンクとして読む（前後の空白と囲む二重引用符を落とす。ほかの引数は、いままでどおり使わない）。起動のいちばん初めに、この起動が使うはずのdataの場所（`storage_state_configured_directory`。確かめも作りもしない）で動いている窓を探し、渡せたら何も作らずに終わる。渡せなければふつうに起動し、窓ができたら開く。
    「使用中」で断られた後に渡すのではなく、先に渡してみる形にした: 2つ目の起動が場所の確かめや「使用中」の箱まで進まない。
  - 分かっている限界: dataの場所はbyteで比べる。同じフォルダを別のつづり（大文字小文字・短い名前・substのドライブ）で起動すると渡せず、いままでどおり「使用中」になる。動いているアプリが次回のdataの場所を変えた直後は、2つ目の起動は新しい場所を見るので、動いている窓へは渡らない。
  - 開く前の同期（`synchronize`）は、待っていた台帳の書き込みや改名の続きを行うことがある。開くことで編集中のノートが保存される（ドロワーのクリックと同じ）。リンクが新しく何かを作る・消すことは無い。

## 検証

- 窓と入口（#1097、[品質記録](../quality/2026-11-20-open-link.md)）: 実窓の試験`open_link_native`（箇所の選択5つ、断る場面、面が開いているあいだ、`WM_COPYDATA`の受け渡し＝別のdataは受けない、起動の引数の読み取り、動いている窓への受け渡し、編集表示から）。単体は対応表の逆引きと、dataの場所だけを引く窓口。

- 中核とapplication（#1095）: 単体の試験（不正な形・値・名前・上限・ちょうどの大きさのバッファでの端・確保の失敗、箇所探しの「あたり」の端と改行の形、台帳を読み直してからの位置引き）。独立レビューは欠陥なし（改善の指摘を取り込んだ）。シンボル検査で、中核に許可されていない`memchr`を使っていたのを見つけて外した。
