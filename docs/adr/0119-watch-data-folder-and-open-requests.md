# ADR 0119: dataフォルダの外からの変更を見つけて読み直し、依頼のファイルで開く

Status: accepted / 2026-11-20 / Issue #1070・#1071（hideの判断: 2026-11-20、[判断のページ](https://claude.ai/artifact/Aa176DzvdKiBx26BQDbyBu)の5点は「全部推し」。決定はまだどれも窓まで実装していない。実装した段階をこの文書に書き足す）

## 背景

- [ADR0117](0117-refresh-ledgers-before-write.md)（#1069）で、台帳を書く操作は書く前に読み直すようになった。外で足したノートは消えないが、**操作をするまで一覧に出ない**。
- [ADR0118](0118-open-note-by-link.md)（#1071）で、リンクを受けてノートを開けるようになった。ただしリンクのクリックで開くにはWindowsへの登録が要り、ZIP版は登録しない。WSL側のLLMはWindows側の実行ファイルを起動しない。LLMからの主な道として、**依頼のファイル**（`data/.requests/`）が要る。
- どちらも「dataフォルダの変更を見つける」ことが土台になる。SPECIFICATIONの「やらないこと」には「背景スレッド（C-013）」があり、これは変えない。

いまのコード（2026-11-20に確認）:
- メッセージの待ちは`src/app/main.c`の`run_message_loop`（`PeekMessageW` → 空なら窓のidleの仕事 → 無ければ`WaitMessage`。ADR0068）。見張りの処理は無い。
- 読み直しの部品は揃っている（`refresh_notes`・`refresh_categories`。ディスクとメモリが同じなら何もしない。採用は名前で付け替える）。
- 保存のときの「外で変わった」の照合は既にある（`NOTE_STORE_SOURCE_CHANGED`。保存を止めて知らせる）。
- 「開く」依頼の検証（`open_request`）、箇所探し（`open_place`）、開く入口（`folio_window_open_link`＝預かって待ちの先頭で開く）は#1071で揃った。

## 決定

1. **見つけ方: スレッドを増やさず、変更の通知のハンドルをメッセージの待ちに加える。**
   - `adapters/win32`に見張りのアダプタを足す。`FindFirstChangeNotificationW`で`data/`の下（サブツリー、ファイル名・フォルダ名・最終更新）を見る。ハンドルはこのアダプタが持つ。
   - 入口の待ちを`WaitMessage`から`MsgWaitForMultipleObjects`（メッセージか、このハンドル）へ替える。ハンドルが立ったら`FindNextChangeNotification`で張り直し、窓へ「dataが変わった」を1回知らせる。UIスレッドだけで動く（C-013を保つ）。
   - 保険として、窓が前面に戻ったとき（`WM_ACTIVATEAPP`）にも1回確かめる（通知を取りこぼしたとき、ネットワークのフォルダなど通知が来ない場所）。（hideの判断1: すぐ見つける＋前面に戻ったときも確かめる）
   - 見張りを張れなかったとき（場所が通知に対応していないなど）は、黙って「前面に戻ったときだけ」に落ちる。起動は止めない。
2. **まとめて、静かなときにだけ読み直す。**
   - 自分の保存でも通知は立つ。通知のたびには読み直さない。最後の通知から短い間（300ミリ秒）を置いてから、1回だけ読み直す。
   - 読み直すのは、窓が何も持っていない静かなときだけ: 面・OSのダイアログ・ドラッグ・削除・終了・変換・流し込みの途中ではない（リンクで開くときの「断る条件」と同じ判定を使う）。途中なら、終わるまで待ってから読み直す（捨てない）。
     理由（#1069の教訓）: 読み直しは一覧を入れ替える。番号を持っている面の下で入れ替えると、別のノートやカテゴリに操作が当たる。
   - 読み直して同じなら、何も起きない（描き直しも、知らせも無い）。
3. **読み直す範囲**
   - カテゴリの台帳と、すべてのカテゴリのノートの台帳（閉じているカテゴリも。開いたときに古い一覧が一瞬見えるのを避ける）。
   - 開いているノートが閲覧表示で、ファイルが変わっていたら、本文を読み直して描き直す。読んでいた位置（スクロール）はできるだけ保つ。（hideの判断2）
   - 検索の準備済みの索引（本文の写し）は、一覧を採用したときに作り直す（#1069の部品がそうしている）。本文だけが変わったノートは、そのノートの写しだけを読み直す。
4. **編集中のノートが外で変わったとき: 知らせるだけで、編集には触らない。**
   - 1行で、このノートが外で変更されたことを知らせる。編集中の本文もUndoもそのまま。その場で「読み直す／自分の編集を残す」を選ばせる面は、作らない。（hideの判断3）
   - **保存のときの扱いは未決（hideに確認し直す）。** 判断のページとこの文書の最初の版には「保存のときは、既存の照合が働いて上書きを止める」と書いたが、**事実と違った**（設計席の誤り。2026-11-20の夜にコードで確かめた）。
     - 外の変更と照らして保存を止める道（`NOTE_SAVE_CHECK_CURRENT` → `NOTE_STORE_SOURCE_CHANGED`、「ファイルの内容が変わったため保存していません。編集中の本文は残っています。」）を使っているのは、タグの管理を開く前の保存の1か所だけ。
     - ふつうの保存（Ctrl+S、ノートの切り替え、終了のとき）は照らさずに上書きする。上書きの前に、いまのファイルを読んで履歴へ送る（`store_note`、ADR0093）ので、外の版は履歴には残る。
     - 選ぶ案: (A) いままでどおり上書きし、1行で「保存すると上書きします（外の版は履歴に残ります）」と伝える。(B) ふつうの保存も照らして、外で変わっていたら保存を止める（既存の文。利用者は「名前を付けて保存」で自分の版を残すか、編集を破棄して読み直す）。(C) 保存のときに選ばせる面を出す。
     - 設計席の推しは(B): hideが選んだ「知らせるだけ・編集に触らない・保存のときに確かめる」にいちばん近く、黙って上書きすることが無くなる。決まるまで、段取りの3の「編集中」の枝は作らない。
5. **知らせ**
   - 見張りが一覧を読み直して変わったとき、1行は出さない（外で足したノートが一覧に現れること自体が知らせ。頻繁に出るとうるさい）。（hideの判断4）
   - 開いているノート（閲覧）を読み直したときは、1行「外部の変更を読み込みました」を出す（読んでいる文が変わるので）。
6. **依頼のファイル**（#1071の2）
   - 置き場所は`data/.requests/`。ファイル名は`open-<何でも>.json`。中身は`{"version":1,"action":"open","category":"…","note":"…","lines":"3-8","text":"…"}`（`lines`と`text`は任意）。
   - 見張りが見つけたら、読んで、リンクと同じ検証（`open_request`。欄から作る入口を足す。規則は同じ）を通し、同じ入口（預かって待ちの先頭で開く）へ渡す。処理したら消す。
   - 形が正しくないもの・知らない`action`・知らない`version`のものは、開かずに消す。64KiBを超えるファイルは読まずに消す。
   - 複数あれば、更新の古い順に1つずつ。
   - **アプリが動いていないあいだに置かれた依頼**は、起動のときに、更新から5分以内のものだけを開き、古いものは消す。（hideの判断5）
   - `.requests`は一覧・履歴・書き出し・走査に入れない。カテゴリの名前の規則が先頭の`.`を拒むので、いまの走査も拾わないはず（実装のときに実ファイルの試験で確かめる）。
   - 書き込みの依頼は作らない。依頼のファイルを置く側（LLM）に結果を返す仕組みも作らない（開いたかどうかは画面で分かる）。
7. **層**
   - `adapters/win32`: 見張りのハンドル、依頼のファイルの一覧・読み・削除（ファイルを読むのはここだけ＝ARC-007）。
   - `application`: 「dataが変わった」を受けて読み直す意図（全カテゴリの読み直し、開いているノートの本文の照合）、依頼のポート。
   - `core`: 依頼のJSONの読み（既存のJSON読みと`open_request`）。
   - `ui/win32`: まとめるタイマー、静かなときの判定、描き直し、1行。
   - `app`: 待ちの形（`MsgWaitForMultipleObjects`）。
8. **やらないこと**: 背景スレッド、ファイルごとの細かい差分の追跡（`ReadDirectoryChangesW`の非同期の読み）、外の変更の自動の取り込み方の選択（マージ）、依頼の結果の返信、書き込みの依頼。

## 理由

- `FindFirstChangeNotificationW`は「何かが変わった」だけを知らせ、何が変わったかは言わない。読み直しの部品が「同じなら何もしない」ので、それで足りる。何が変わったかを知る`ReadDirectoryChangesW`は、非同期の読みとバッファの管理が要り、取りこぼしの扱いも増える。
- 待ちにハンドルを加える形なら、スレッドも、スレッド間の受け渡しも要らない。入力がある間はメッセージが先に処理され、見張りは待ちのときにだけ見る。
- 編集中に外の変更を取り込む選択を迫ると、書いている最中に邪魔をする。保存のときに止める仕組みは既にあり、そこで決めれば足りる。

## 段取り（PRごとに緑）

1. この文書、SPECIFICATION（新しいFRと「やらないこと」の書き換え）、用語。
2. application: 全カテゴリを読み直す意図と、開いているノートの本文の照合。単体の試験（偽の保存先で外の変更を再現）。
3. ui: 窓が前面に戻ったときに、静かなら読み直す（見張りのハンドルは無し。ここまでで「戻ってきたら新しい」が成り立つ）。実窓の試験。
4. adapters / app: 見張りのハンドルと、待ちの形。まとめるタイマー。実ファイルの試験（動いている間に外で`.md`を足す → 何もしなくても一覧に出る）。起動直後のCPU（入力なし20秒）を測る。
5. 依頼のファイル: ポート、JSONの読み、処理して消す。実ファイルと実窓の試験。
6. LLM向けの使い方の文書（依頼のファイルの書き方、リンクの書き方）。
