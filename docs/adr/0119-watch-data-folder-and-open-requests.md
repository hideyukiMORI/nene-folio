# ADR 0119: dataフォルダの外からの変更を見つけて読み直し、依頼のファイルで開く

Status: accepted / 2026-11-20 / Issue #1070・#1071（hideの判断: 2026-11-20、[判断のページ](https://claude.ai/artifact/Aa176DzvdKiBx26BQDbyBu)の5点は「全部推し」。決定はまだどれも窓まで実装していない。実装した段階をこの文書に書き足す）

## 背景

- [ADR0117](0117-refresh-ledgers-before-write.md)（#1069）で、台帳を書く操作は書く前に読み直すようになった。外で足したノートは消えないが、**操作をするまで一覧に出ない**。
- [ADR0118](0118-open-note-by-link.md)（#1071）で、リンクを受けてノートを開けるようになった。ただしリンクのクリックで開くにはWindowsへの登録が要り、ZIP版は登録しない。WSL側のLLMはWindows側の実行ファイルを起動しない。LLMからの主な道として、**依頼のファイル**（`data/.requests/`）が要る。
- どちらも「dataフォルダの変更を見つける」ことが土台になる。SPECIFICATIONの「やらないこと」には「背景スレッド（C-013）」があり、これは変えない。

いまのコード（2026-11-20に確認）:
- メッセージの待ちは`src/app/main.c`の`run_message_loop`（`PeekMessageW` → 空なら窓のidleの仕事 → 無ければ`WaitMessage`。ADR0068）。見張りの処理は無い。
- 読み直しの部品は揃っている（`refresh_notes`・`refresh_categories`。ディスクとメモリが同じなら何もしない。採用は名前で付け替える）。
- 保存のときの「外で変わった」の照合は既にある（`NOTE_STORE_SOURCE_CHANGED`。保存を止めて知らせる）。
- 「開く」依頼の検証（`open_request`）、箇所探し（`open_place`）、開く入口（`folio_window_open_link`＝預かって待ちの先頭で開く）は#1071で揃った。

## 決定

1. **見つけ方: スレッドを増やさず、変更の通知のハンドルをメッセージの待ちに加える。**
   - `adapters/win32`に見張りのアダプタを足す。`FindFirstChangeNotificationW`で`data/`の下（サブツリー、ファイル名・フォルダ名・最終更新）を見る。ハンドルはこのアダプタが持つ。
   - 入口の待ちを`WaitMessage`から`MsgWaitForMultipleObjects`（メッセージか、このハンドル）へ替える。ハンドルが立ったら`FindNextChangeNotification`で張り直し、窓へ「dataが変わった」を1回知らせる。UIスレッドだけで動く（C-013を保つ）。
   - 保険として、窓が前面に戻ったとき（`WM_ACTIVATEAPP`）にも1回確かめる（通知を取りこぼしたとき、ネットワークのフォルダなど通知が来ない場所）。（hideの判断1: すぐ見つける＋前面に戻ったときも確かめる）
   - 見張りを張れなかったとき（場所が通知に対応していないなど）は、黙って「前面に戻ったときだけ」に落ちる。起動は止めない。
2. **まとめて、静かなときにだけ読み直す。**
   - 自分の保存でも通知は立つ。通知のたびには読み直さない。最後の通知から短い間（300ミリ秒）を置いてから、1回だけ読み直す。
   - 読み直すのは、窓が何も持っていない静かなときだけ: 面・OSのダイアログ・ドラッグ・削除・終了・変換・流し込みの途中ではない（リンクで開くときの「断る条件」と同じ判定を使う）。途中なら、終わるまで待ってから読み直す（捨てない）。
     理由（#1069の教訓）: 読み直しは一覧を入れ替える。番号を持っている面の下で入れ替えると、別のノートやカテゴリに操作が当たる。
   - 読み直して同じなら、何も起きない（描き直しも、知らせも無い）。
3. **読み直す範囲**
   - カテゴリの台帳と、すべてのカテゴリのノートの台帳（閉じているカテゴリも。開いたときに古い一覧が一瞬見えるのを避ける）。
   - 開いているノートが閲覧表示で、ファイルが変わっていたら、本文を読み直して描き直す。読んでいた位置（スクロール）はできるだけ保つ。（hideの判断2）
   - 検索の準備済みの索引（本文の写し）は、一覧を採用したときに作り直す（#1069の部品がそうしている）。本文だけが変わったノートは、そのノートの写しだけを読み直す。
4. **編集中のノートが外で変わったとき: 知らせるだけで、編集には触らない。**
   - 1行で、このノートが外で変更されたことを知らせる。編集中の本文もUndoもそのまま。その場で「読み直す／自分の編集を残す」を選ばせる面は、作らない。（hideの判断3）
   - **保存のとき: ふつうの保存でも外の変更と照らし、変わっていたら保存を止める（hideの判断: 2026-11-20夜、案B）。** 編集中の本文は残る。黙って上書きしない。
     - 経緯: 判断のページとこの文書の最初の版には「保存のときは、既存の照合が働いて上書きを止める」と書いたが、事実と違った（設計席の誤り）。照らして止める道（`NOTE_SAVE_CHECK_CURRENT`）を使っていたのはタグの管理を開く前の保存だけで、ふつうの保存（Ctrl+S・ノートの切り替え・終了）は照らさずに上書きしていた（外の版は履歴に残る）。hideに選び直してもらい、(A) いままでどおり上書きして伝える／(B) ふつうの保存も照らして止める／(C) 選ばせる面、から(B)に決まった。
     - 編集が無いとき（本文が読み込んだものと同じ）は照らさない。外で消えていたファイルは、止めずに作り直す（上書きするものが無い。ADR0117）。読めないファイルへの保存の結果は、これまでと同じ（履歴を残せないので保存しない）。
     - **この決定は、次の2つと一緒でなければ入れない**（独立レビュー、2026-11-20。枝`feat/1070-guarded-save`は未統合）:
       - **外の版を読み直す出口。** いまの「編集を破棄する」（`:e!`）はメモリの本文へ戻すだけで、ディスクを読まない。同じノートを選び直しても読まない。保存が止まった後に外の版を得る道が「破棄 → 別のノートへ → 戻る」しか無い。「編集を破棄して、ディスクから読み直す」を作る。
       - **閲覧中の読み直し（段取りの3）。** 閲覧中に外で変わったノートを、読み直さないまま編集に入ると、入力した後の保存が必ず止まる。編集に入る前に読み直されていなければならない。
     - 止まったときの1行は、次の一手（別の名前で保存／破棄して読み直す）を言う文に直す。終了のとき（窓を閉じる・Windowsの終了）に止まった場合の出口も、文で示す。
5. **知らせ**
   - 見張りが一覧を読み直して変わったとき、1行は出さない（外で足したノートが一覧に現れること自体が知らせ。頻繁に出るとうるさい）。（hideの判断4）
   - 開いているノート（閲覧）を読み直したときは、1行「外部の変更を読み込みました」を出す（読んでいる文が変わるので）。
6. **依頼のファイル**（#1071の2）
   - 置き場所は`data/.requests/`。ファイル名は`open-<何でも>.json`。中身は`{"version":1,"action":"open","category":"…","note":"…","lines":"3-8","text":"…"}`（`lines`と`text`は任意）。
   - 見張りが見つけたら、読んで、リンクと同じ検証（`open_request`。欄から作る入口を足す。規則は同じ）を通し、同じ入口（預かって待ちの先頭で開く）へ渡す。処理したら消す。
   - 形が正しくないもの・知らない`action`・知らない`version`のものは、開かずに消す。64KiBを超えるファイルは読まずに消す。
   - 複数あれば、更新の古い順に1つずつ。
   - **アプリが動いていないあいだに置かれた依頼**は、起動のときに、更新から5分以内のものだけを開き、古いものは消す。（hideの判断5）
   - `.requests`は一覧・履歴・書き出し・走査に入れない。カテゴリの名前の規則が先頭の`.`を拒むので、いまの走査も拾わないはず（実装のときに実ファイルの試験で確かめる）。
   - 書き込みの依頼は作らない。依頼のファイルを置く側（LLM）に結果を返す仕組みも作らない（開いたかどうかは画面で分かる）。
7. **層**
   - `adapters/win32`: 見張りのハンドル、依頼のファイルの一覧・読み・削除（ファイルを読むのはここだけ＝ARC-007）。
   - `application`: 「dataが変わった」を受けて読み直す意図（全カテゴリの読み直し、開いているノートの本文の照合）、依頼のポート。
   - `core`: 依頼のJSONの読み（既存のJSON読みと`open_request`）。
   - `ui/win32`: まとめるタイマー、静かなときの判定、描き直し、1行。
   - `app`: 待ちの形（`MsgWaitForMultipleObjects`）。
8. **やらないこと**: 背景スレッド、ファイルごとの細かい差分の追跡（`ReadDirectoryChangesW`の非同期の読み）、外の変更の自動の取り込み方の選択（マージ）、依頼の結果の返信、書き込みの依頼。

## 理由

- `FindFirstChangeNotificationW`は「何かが変わった」だけを知らせ、何が変わったかは言わない。読み直しの部品が「同じなら何もしない」ので、それで足りる。何が変わったかを知る`ReadDirectoryChangesW`は、非同期の読みとバッファの管理が要り、取りこぼしの扱いも増える。
- 待ちにハンドルを加える形なら、スレッドも、スレッド間の受け渡しも要らない。入力がある間はメッセージが先に処理され、見張りは待ちのときにだけ見る。
- 編集中に外の変更を取り込む選択を迫ると、書いている最中に邪魔をする。保存のときに止める仕組みは既にあり、そこで決めれば足りる。

## 段取り（PRごとに緑）

1. この文書、SPECIFICATION（新しいFRと「やらないこと」の書き換え）、用語。
2. application: 全カテゴリを読み直す意図と、開いているノートの本文の照合。単体の試験（偽の保存先で外の変更を再現）。
3. ui: 窓が前面に戻ったときに、静かなら読み直す（見張りのハンドルは無し。ここまでで「戻ってきたら新しい」が成り立つ）。実窓の試験。
4. adapters / app: 見張りのハンドルと、待ちの形。まとめるタイマー。実ファイルの試験（動いている間に外で`.md`を足す → 何もしなくても一覧に出る）。起動直後のCPU（入力なし20秒）を測る。
5. 依頼のファイル: ポート、JSONの読み、処理して消す。実ファイルと実窓の試験。
6. LLM向けの使い方の文書（依頼のファイルの書き方、リンクの書き方）。

  - **「編集」の操作で閲覧から編集に入るとき**（`execute_mode_command`）にも同じ確かめをして、変わっていれば読み直してから編集に入る（決定4の「編集に入る前に読み直されていなければならない」。窓を前面にしたまま外で変わった場合の備え。面が開いているときは読み直さない）。編集から閲覧へ戻ったとき（`flush_edit`）は、**その場で**ノートのファイルを確かめて読み直す（一覧は読まない）。最初の版は印を立てて待ちへ回していたが、独立レビューが欠陥を見つけた: 編集中のノートへのリンクや検索の一致は、閲覧へ戻した直後に箇所を選ぶので、後から読み直すと、古い本文で選んだ箇所が消える。
  - 編集に入る共通の関数（`enter_edit`）には置かない: ほかの呼び手（タグの適用・「ここを編集」・検索の一致から開く）は、いまの本文から作った位置を持って入るので、そこで本文を入れ替えると位置がずれる。これらの入口で、窓を前面にしたまま外で変わったノートを編集し始める場合は、段取りの4の見張りが先に読み直す。
  - 読み直した後の同じ待ちの回で、前からあった仕事（検索の準備・ミニマップ）も1単位進める（読み直しが待ちの回を1つ取らない）。
  - 一覧やファイルが読めないときは、ここでは何も出さない（決定2と#1106のレビュー）。
- 決定4の「保存のときに照らして止める」（#1107、2026-11-21）: 入れた。条件の2つ（閲覧中の読み直し＝段取りの3、編集を破棄してファイルから読み直す）と一緒。
  - 保存の依頼に`recreate`（無ければ作ってよい）を足し、ふつうの保存（`NOTE_SAVE_EDITS`）も期待する本文を渡す（`store_edited`）。アダプタの保存の入口は1つのまま（`store_note`。ADR0093）。
  - **編集を破棄して読み直す**（`:e!`、`execute_discard_command`）は、`folio_state_reload_document`でファイルから読み直してから本文を流し込む。ファイルが無い・読めないときと無題は、これまでどおり最後に読んだか保存した本文へ戻す。外の版を読んだときは1行を出す。名前のあるノートのファイルを読み直せなかったときも、そのことを1行で言う（外でテキストでなくなったファイルは、破棄しても外の版を読めない。黙って古い本文へ戻すと、次の保存がまた同じ文で止まる＝独立レビューの指摘）。
  - 止まったときの1行は、次の一手（別名で保存／編集を破棄して読み直す）を言う文にした。この1行は本文の下の1行の帯に出て、幅が足りないと末尾が省略されるので、理由を短くして次の一手が先に来るようにした（独立レビュー。画素の幅は測っていない。全文はツールチップと読み上げにある）。窓を閉じるとき・`:wq`も同じ1行で、窓は残る（`:q`は保存しないので、これまでどおり未保存を理由に断る。保存せずに終了は`:q!`）。Windowsの終了は、これまでどおり「保存処理が未完了です。保存を再試行してください。」で断る（外の変更のままでは再試行も止まる。そのときに上の1行が出る）。
  - 外でテキストでなくなったファイル（不正なUTF-8・NUL）へのふつうの保存は、「ノートを読めません」ではなく外の変更として止める。開けないファイルは、これまでどおり「履歴を残せない」。
  - 「編集」・「閲覧」の操作の途中で外の変更を読み込んだときの1行が、面を隠す処理で消えていた（段取りの3の見落とし）。立て直すようにした。
- 段取りの4（#1117、2026-11-21）: 見張りを入れた。
  - `adapters/win32`の`data_watch`: `FindFirstChangeNotificationW`（dataの下のサブツリー、ファイル名・フォルダ名・最終更新）。ハンドルはこのアダプタが持ち、外へ出さない。
  - **決定7の「app: 待ちの形」からの補正**: ハンドルを外へ出さないために、待つ関数（`data_watch_wait`＝`MsgWaitForMultipleObjectsEx`）と、次の知らせを頼む関数（`data_watch_listen`＝`FindNextChangeNotification`）もアダプタに置いた。入口のループ（`PeekMessageW` → 待ちの先頭の仕事 → 待つ）と、戻った理由での振り分け（`wait_for_work`）は`app`のまま。見張りを張れなかったとき・張り直せなくなった後は、これまでどおり`WaitMessage`で待つ。
  - **決定2の「最後の通知から300ミリ秒」からの補正（独立レビュー）**: 変化で待ちが戻ったら、まとめの時間が過ぎるまで次の知らせを頼まない（そのあいだの待ちはメッセージだけ。そのあいだの変化はOSが覚えていて、頼んだ直後に知らされる）。最初の版は、知らせのたびに張り直してタイマーを掛け直していた。それだと、知らせをすぐ出し直す場所（一部のネットワークの共有など）では待ちが空回りしてCPUを使い切り、書き込みが続くあいだは読み直しが来なかった。いまの形は、どちらの場合も「300ミリ秒に1回まで」になる。
  - 窓: 最初の知らせで300ミリ秒のタイマーを掛け（`folio_window_data_changed`。まとめている最中の知らせは何もしない）、鳴ったら段取りの3の印（`outside_due`）を立てる。合成ルートは、まとめている最中（`folio_window_data_settling`）は次の知らせを頼まない。読むのは、段取りの3と同じく窓が静かなとき。アプリ自身の保存でも知らせは来るが、読み直しは同じなら何もしない（一覧は変わらず、開いているノートは保存した本文とファイルが同じ）。
  - 見張りは、一覧を読む前に張る（読んでから待ちに入るまでの変化を取りこぼさない）。見る変化は、ファイル名・フォルダ名・大きさ・最終更新。
  - 知らせを頼めなくなったら（保存先が外れたなど）、その起動のあいだは見張りを閉じ、メッセージだけを待つ（戻ったときの読み直しは残る。張り直しは試みない）。

  - app: 起動のときに1回、知らせがあったものとして見る（`folio_window_data_changed`）。
  - **決定6からの補正**:
    - 「5分より古いものは消す」は、起動のときに限らず、見つけたとき常に当てる（置かれてから5分のあいだ窓が静かにならなかった依頼も消える）。規則を1つにするため。
    - 中身を渡すのは、ファイルを消せたときだけにした（消せないファイルを渡すと、見るたびに同じノートを開き続ける）。消せないファイル・いま読めないファイルは、そのままにして次を見る。読み取り専用の印は外して消す（WSLなどから置くと付くことがある）。
    - 古すぎ・大きすぎのファイルは、フォルダを並べる段で消して、候補に入れない。候補は古いほうから32個まで（独立レビュー: 消せないファイルが32個たまると、新しい依頼が見えなくなっていた。いまは、候補を塞ぐのは5分以内のファイルだけで、5分たてば候補から外れる）。
    - 「同じ入口（預かって待ちの先頭で開く）」ではなく、読み直しの静かな回の中で、そのまま開く。静かでないあいだはファイルが待つので、リンクの「ほかの操作の途中です」の1行は出ない。
    - 正しくないファイルは、1回の呼び出しの中で続けて捨てる（32個まで）。1つごとに一覧を読み直さない。正しい依頼は1回に1つで、次は次の静かな回。
    - 道の組み立ては、長さを確かめてから行う（独立レビュー: `swprintf_s`は収まらないとプロセスを止める。外から来る名前で起動できなくなりえた）。長すぎる道のファイルは見ない。
  - 書き手が開いたままのファイルは読めないので、消さずに待つ。書き手が何度かに分けて開き直して書くと、途中の形を読んで、正しくないものとして消す恐れがある。確実なのは、別の名前で書き終えてから、すぐ`open-*.json`へ名前を変えること（5分の規則は更新の日時で見る。段取りの6の文書に書く）。UTF-16のファイル（Windows PowerShell 5の`>`）は正しくないものとして消える。
  - **編集している最中の依頼（#1152、2026-11-22。hideの判断）**: 名前のあるノートを編集していて保存していない変更があるときは、黙って保存して切り替えるのをやめ、面を出して選んでもらう。
    - hideの判断（11月22日 3時台）: 「モーダルでどうするか聞く。編集中のものは接頭辞にインデックスつけて逃がすかとか。」細部の6つ（[選ぶページ](https://claude.ai/artifact/F2HvbiNXt2gfQz4SBXzbdZ)）は、11月22日の昼に「全部推しでいいよ」。
    - 面（`request_prompt`）: 3つを縦に並べる。「保存して開く」（既定・Enter）／「別の名前で残して開く」／「開かない」（Esc・×）。どの釦にも、押すと何が起きるかを1行で添える。塗りは`dialog_theme`（名前入力面・失敗の箱と同じ）。
    - 別の名前: `1_元の名前`。もうあれば`2_`…と、空いているいちばん小さい番号（大文字小文字を区別せずに比べる。1000まで）。同じカテゴリの新しいノートとして保存し（別名保存と同じ道）、元のノートのファイルと履歴は書かない。名前を決めるのはcoreの`note_name_numbered`とapplicationの`folio_state_aside_name`、保存は`folio_state_keep_aside`。
    - 「開かない」を選んだ依頼は消える（依頼のファイルは、取ったときに消している。あらためて消す処理は無い）。
    - 面を出しているあいだに届いた依頼: 答えの後の静かな回で、たまった中のいちばん新しい1つだけを扱う（`folio_state_take_last_open_request`。古いものは捨てる）。そのときも保存していない変更が残っていれば、もう一度聞く。
    - 5分の決まり: 面を出した依頼は、もう取ってあるので、答えるまで待つ（面は勝手に消えない）。面のあいだにたまった依頼のうち、5分より古いものは、これまでどおり見つけたときに消える。
    - リンク（FR-057）: これまでどおり、保存してから開く（利用者の操作なので）。無題の下書き: 離れるときのいつもの面が聞く（変えない）。保存していない変更が無いとき: 聞かずに開く。
    - 残す名前を作れないとき（番号が尽きた・名前が長すぎる）は、面を出さずに失敗を知らせ、依頼は開かない。
    - **面が出た直後の鍵は、答えにしない**（独立レビューの指摘）: 面は、利用者の操作と関係なく出る。本文を打っている最中に出ると、打っていた字（空白・Enter・S / K / N）が、そのまま答えになってしまう。面の釦は、鍵が止まってから0.7秒が過ぎるまで、鍵を受けない（受けずに捨て、捨てるたびに数え直す）。マウスとAlt+字は、はじめから効く。変換の途中は、もともと依頼を見に行かない。
    - 「保存して開く」は、いつものリンクの道（切り替えるときに保存する）を通る。依頼のノートやカテゴリが見つからないときは、切り替えないので、保存もしない（編集中の本文は、未保存のまま残る。1行で「見つかりません」と知らせる）。
    - 「別の名前で残して開く」で残した名前は、開いた後に1行で言う。開く側が言うこと（ノートが無い・箇所が無い）があるときは、そちらを残す（残した名前は、題に出ている）。依頼のノートが無ければ、残したノートを開いたままになる。
    - 面を作れなかったとき（記憶や資源の不足）は、依頼を開かずに、失敗を知らせる。
    - 残っていること: 説明の行は、読み上げでは釦の名前に付かない（釦の後ろの文として、順に読めば届く）。主窓がとても小さいと、面の下の釦が収まらないことがある。面の見た目の受理は、hideの実画面の判断（まだ）。
  - 対応していないもの: リンク（シンボリックリンクなど）の先を読むこと（消えるのはリンクそのもので、dataの外は消えない。読むのは16MiBまでで、渡すのは64KiBまで）、取り出した後の記憶不足（依頼は消えている）。
