# ADR 0121: Markdownの読みは仕様に準拠するのが基本で、外すときは理由を書いたFolioの決まりにする

Status: accepted / 2026-11-22 / Issue #1190（hideの判断: 2026-11-22の夜「基本はmdに準拠で理由があればFolioルールを作ることを検討というスタンスで行きたい」）

## 背景

2026-11-22に、中核の単体の試験を足す作業の中で、Markdownの読みの出方をCommonMarkの定義と1つずつ照らした（[品質記録](../quality/2026-11-22-core-branches.md)）。
ずれが見つかるたびに、「これは意図した仕様なのか、合わせ忘れなのか」が文書から読み取れなかった:

- リンクの宛先の`a\ b`（#1158）と、見出しの終わりの`#`の並び（#1188）は、合わせ忘れと見て直した。
- 空白の無い`#`だけの行が段落になること、字下げ4つのコードブロックが段落になることは、既存の試験がその形で固定していたので、席は判断待ちにした。

[使い方の文書](../MARKDOWN.md)は「CommonMark/GFMの全構文への完全互換は保証しません」と書いているが、どこを・なぜ外しているかの一覧は無い。
仕様と違う振る舞いが「決めたこと」なのか「まだやっていないこと」なのかを、試験の有無では区別できない。

## 決定

1. **Markdownの読みと表示は、仕様に準拠するのが基本。** ここで言う仕様は、CommonMarkの本体（リナの解釈。表・チェックの印・脚注などの拡張は、Folioが採ると決めたものだけで、それぞれのADRが正本）。
2. **仕様から外すのは、理由があるときだけ。** 外すと決めたものは「Folioの決まり」として、理由と一緒に、該当するADRと[使い方の文書](../MARKDOWN.md)に書く。
3. **理由の書いていないずれは、合わせ忘れとして扱う。** 既存の試験が仕様と違う形を固定していても、それだけでは決まりと見なさない。見つけたら、判断待ちにせず、仕様に合わせる直しをIssueにして進める。
4. **外す理由がありそうなとき**（表示の都合、既存のノートの見え方が大きく変わる、実装の重さに見合わない、など）は、理由を添えてhideに出す。決まったら2のとおりに書く。
5. **まだ対応していない記法**（[使い方の文書](../MARKDOWN.md)の「対応範囲」に挙げているもの: HTMLの描画、数式、など）は、この決定で「外すと決めた」ことにはならない。対応するかどうかは、それぞれ別に決める。

## この決定で動かすこと

| ずれ | 扱い |
| --- | --- |
| 空白の無い`#`だけの行（`#`・`##`）が段落になる | 仕様に合わせて、空の見出しにする（#1190） |
| 字下げ4つのコードブロックが、普通の段落として出る | 仕様に合わせる。読みの仕組み（リストの継続や引用との重なり）に触るので、別のIssueで設計から進める |

## 結果

- 仕様とのずれを見つけた席は、迷わず直しへ進める。仕様と違う振る舞いには、必ず読める理由がある状態になる。
- 既存のノートの見え方が変わることがある（今回の2つは、どちらも珍しい書き方）。保存ファイルは変えない（表示だけ）。
- 製品の振る舞いが変わるので、直しはmainへ入れる前に独立レビューを通す。

## 検討して採らなかった案

- **ずれを見つけるたびにhideへ聞く**: 判断待ちが積み上がり、同じ問いを繰り返すことになる（今日だけで4件）。
- **いまの振る舞いを全部「Folioの決まり」として文書に固定する**: 合わせ忘れまで決まりになり、ほかのMarkdownの道具と見え方が違う理由を説明できない。
