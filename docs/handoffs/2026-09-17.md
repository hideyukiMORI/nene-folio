### 役割と運用（本日確立した手順）

- 設計・判断・ADR・レビュー依頼・統合は設計リナ（Fable）。実装・調査・読み取り専用レビューはOpusの実装リナを背景で立ち上げ、報告で詰める。
  各PRは「ADRを先に枝へ置く → 実装（層ごとにコミット）→ 別のOpusの読み取り専用レビュー → 止める所見を同じPRで修正 → 最終SHAでフルゲート → Ready → CI → squash merge」。
  判定1か所などの小さな差分は設計リナが直接読んでレビューを省く。
- 実装リナが利用上限で途中終了したら、同じagentへメッセージを送ると文脈を保って再開できる（#40で実績）。
- CIは`ready_for_review` / `synchronize` / `edited` / `reopened`でだけ走る。落ちたイベントは`gh pr ready --undo`→`gh pr ready`で再発火。
- PR本文はGIT-004の字面どおりのフィールド行（`目的:`など）。`## 目的`の見出し形式はCIで落ちる。
- mainを作業枝へ取り込むmergeの件名は`chore(sync): … (#N)`。既定の`Merge branch`件名は`validate-git`で落ちる。
- `folio_state_outcome`に値を足すときは既存の2つ目のswitch（`unfinished_failure_line`）へ寄せる。full-enumのswitchを増やすと未到達分岐で被覆が約1ポイント落ちる。
