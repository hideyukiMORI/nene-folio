### 役割と運用（この期間の追加）

- 各 PR の流れは変わらない: 実測 probe → ADR 草案 → 現行コードに照らした読み取り専用の批評 → 受理してコミット →
  実装（層ごとにコミット）→ 独立レビュー → 止める所見を同じ PR で修正 → 最終 SHA でフルゲート → Ready → CI → squash merge。
- **1 つの実装 agent を複数の Issue にまたいで使わない**（文脈が尽きる）。Issue ごとに新しい agent を立て、
  前の単位の事実は ADR・確認記録・引き継ぎから渡す。
- **ADR が未定義の規則 ID を名指しすると CNF-006 で落ちる。** 新しい ID は定義する単位の同じコミットで
  `docs/QUALITY_GATES.md` / `docs/CODING_RULES.md` に **planned** で置き、強制マトリクスの行も同時に足す。
  `docs/quality/gate-proofs.md` の証明行は **active にするコミット**で足す（`document_checks` は active のときだけ要求する）。
- **CI が `ready_for_review` で起動しないことがある。** `gh pr ready --undo && gh pr ready` を試し、
  それでも起動しなければ空でない push（`synchronize`）で起こす。
- **使用制限で agent が止まっても、作業木の未コミットの編集から再開できる。** 止めるときは同じ agent へ
  「未コミットを事実の範囲でコミット → 狭い検査 → 最終 HEAD で 1 回だけゲート → push → どこまで済んだかをファイル名・関数名で報告」。
- PR 本文は GIT-004 の字面どおりのフィールド行（`目的:` / `使った正典経路:` / `規則 ID:` / 検証 / `Waivers:` / `残るリスク:` と `Closes #N`）。
  main を作業枝へ取り込む merge の件名は `chore(sync): … (#N)`。
