## 席のメモに足したこと（22日〜23日）

- 背景で流した「コミット → PR → 統合」は、完了の通知ではなく結果の行（`merged`）を読んでから「入った」と言う。
- 製品の振る舞いが変わる変更は、種類を問わず、mainへ入れる前に独立レビューを通す。統合の道具は1本ずつ流す。
- Markdownは仕様に準拠が基本。ずれを見つけたら、判断待ちにせず、直しをIssueにして進める。
- 足した実窓の試験は、出力を見て、本当に走ったことを確かめる（必須の試験に入っていない場合に置くと、全試験が通っても1度も走らない）。
- 構築の出力を途中で切る形（先頭の数行だけを取る）で流さない。構築の処理が残って、次の構築が止まり、試験が古い構築で走る。出力はファイルへ書いて、終わりの値を読む。
- 絵の寸法を「実物」と書く前に、コードの定数と、絵を撮った画面の拡大率を確かめる。
- 置き換えのスクリプトは「済んだ所は飛ばす」形で書き、止まったら、構築と試験を流さない。試験は、構築が通ったときだけ流す（落ちた構築の後の「全試験成功」は、古い構築の結果）。
- 書体を替えるときは、字の幅と行の高さを、96／120／144／192 DPIで測ってから大きさを決める（手元の120 DPIだけでは、幅の差が出ないことがある）。
- 残った処理を止めるときは、名前でまとめて止めない。道（Path）を確かめて、席が起動したpidだけを止める。
