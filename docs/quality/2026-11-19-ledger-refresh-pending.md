# 2026-11-19 台帳を書く直前の読み直し — 第4段（#1069 / ADR0117）

## 何をしたか

ADR0117の第4段。フォルダを先に変えて台帳を後から書く道（初回保存・名前を付けて保存・取り込み、ごみ箱、別のカテゴリへの移動）を、書く前の読み直しに通した。
これで、ノートの台帳（カテゴリごとの`index.json`）を書く道は、改名を除いてすべて読み直してから書く。カテゴリの台帳（`categories.json`）と改名は第5・第6段。次の版で、公開した1.5.0には入らない。

- `synchronize_index`（保留の台帳の同期。これらの道の台帳の書き込みはここ1か所）が、書く前に`refresh_notes`を呼ぶ。読み直せなければ書かず、保留のまま残る。
- `refresh_transfer`: 別のカテゴリへの移動で、移動先の台帳を書く前に、移動元と移動先の両方を読み直す。相手を名前で引き直し、名前の衝突を読み直した台帳で確かめる。
- カテゴリの並べ替えと「別のカテゴリへ移す」の入口でも、知らせを消す（前の意図の知らせを持ち越さない）。

## 見つけたこと

| 見つけたこと | 対応 |
| --- | --- |
| **製品の欠陥（単体の試験が見つけた）**: ごみ箱へ送る途中は、開いているノートの位置が、いま消したノートの位置のままになっている瞬間がある。その位置で名前を引くと、台帳の終わりを越えて読む（AddressSanitizerが止めた） | 位置が台帳の終わりを越えていたら、名前を引かない（`follow_note`と`refresh_notes`の「残す名前」の2か所）。第3段までは、この瞬間に読み直しが走らなかったので出なかった |
| 単体の偽の保存先は、フォルダの中身も覚えていなかった。作ったノートが次の走査に出ず、読み直しで一覧から消えた | 偽の保存先に、カテゴリごとのフォルダ（名前の集合）を持たせた。作成・ごみ箱・移動・改名の完了で変わる。最初に変わるまでは、従来の固定の一覧を返す |
| 偽の保存先は、作りたてのカテゴリにも既定のノート（one/two/three）を返していた | カテゴリを作ったら、空のフォルダと空の台帳にする |
| 偽の保存先は、改名の完了を台帳にもフォルダにも写していなかった（後の読み直しで改名が元へ戻る） | 改名が完了したら、ノートなら名前と台帳を、カテゴリなら台帳とフォルダの持ち主の名前を付け替える |
| 設計席の試験の組み立て違いが1つ（移動先に同じ名前があり、先に「名前が使われている」で断られていた） | 外で消すノートを別のものにした |

偽の保存先の直しは4つ目になった（第3段で台帳、第4段でフォルダ・新しいカテゴリ・改名）。どれも「本物のファイルならもともとそうなる」ことを偽の保存先が写していなかったもので、製品の誤りではない。実ファイルでの試験（第7段）で、偽の保存先と本物の違いが残っていないかを確かめる。

## 試験

単体（`state_tests.c`）:
- `verify_refresh_created_and_binned`:
  - 外で足されたノートが、新しいノートを保存した後の台帳に入る。新しいノートは開いたまま。
  - 外で書き換えた並び・星・足されたノートが、ごみ箱の後の台帳に残る。
  - 台帳を読み直せないときは書かずに保留のまま残り、次の意図が先にそれを書く。
- `verify_refresh_transfer`:
  - 移動元も移動先も外で変わっているとき、外の並びの上で、置いた先のノートの前に入る。両方の一覧に外のノートが出る。
  - 移動先に同じ名前が外から来ていたら、何も書かずに断る（台帳の書き込みもファイルの移動も増えない）。
  - 動かすノートが外で消えていたら、動かさない。

既存の単体の試験は、偽の保存先を直した後、期待値を変えずにすべて通った。

## 独立レビュー（統合の前。読み取りだけの席）

| 指摘 | 対応 |
| --- | --- |
| 欠陥（いちばん重い）: 保留の再試行はどの意図の最初にも走る。そこで一覧が入れ替わると、呼び出し側が数えたノートの番号が古くなり、別のノートをごみ箱へ送る・星を付ける・移す。ごみ箱では台帳の終わりを越えて読む場合もある | 番号でノートを指す意図（星・並べ替え・移動2つ・選択・ごみ箱）は、再試行で一覧が入れ替わったら行わずに断る（`synchronize_places`）。一覧は新しい内容になり、利用者が指し直す。試験を足した |
| 欠陥（設計）: 読み直せない台帳が1つあると、保留が解けず、開いているノートの保存まで含めて全部の意図が断られ続ける。前は上書きの代わりに自然に直っていた。文言（書き戻せませんでした…次回の起動で揃います）も、この原因には合わない | 次の意図の前の再試行は、読み直せないあいだは書かずに待ち、意図を止めない（`retry_index`）。その台帳を自分で書く意図だけが「読めない」で断る。直し方をADRに書いた。試験を足した |
| 欠陥: 開いているノートをごみ箱へ送るとき、その位置に立つ次のノートを「開いているノート」として残す（外で消えていても一覧と台帳に残る） | 開いているノートを消すときは、選択の位置を台帳の終わりにしてから読み直す。試験を足した |
| 欠陥: 別カテゴリへの移動の最初の確認が古いメモリで行われ、外で消えた同名のノートのせいで断り続ける | 位置の確認だけを先に行い、名前の確認は読み直した後にする。試験を足した |
| 推測: 移動の後に星が外から付いていても、位置を指す移動が通る | 置く先が位置のときは、読み直した後の星で断る |
| 推測: 巻き戻しのとき、同じ名前が外から来ていると、その外のノートが台帳に入る | 「守れないまま残ること」の隙間の中として、ADRに書いた |
| 偽の保存先: 作成・移動が、フォルダに同じ名前があっても成功する | 作成は「名前が使われている」、移動は失敗を返す |
| 偽の保存先: フォルダを持った後に固定の一覧を差し替える試験は、黙って無視される | そのときは試験が落ちるようにした（`folder_add` / `folder_remove`を使う）。既存の試験に該当は無かった |
| 偽の保存先: 作りたてのカテゴリに空の台帳がある（本物は台帳が無い） | 「無い」を返す |
| 文書: 決定4の「改名の前後の名前」は実装が無い、決定5と第4段の結果の食い違い、静かな1行が出る入口、仕様書FR-008の書き出し | ADRと仕様書を直した |

レビュー席が確かめて問題なしとした点: 作成・名前を付けて保存・取り込みでは、新しいノートはすでにメモリの末尾にあり選択されているので、外の変更が無ければ入れ替えは起きない。取り込みは1ファイルごとに同期し、保留が次のファイルへ持ち越されない。移動は、読み直した後の番号を、その後の処理すべてで使っている。保留と未完了の改名は同時に成り立たない。

足していない試験（レビューの一覧のうち）: 取り込みと外で足されたノート、名前を付けて保存、巻き戻し、置く先のノートが消えた移動、移動の2つ目の読み直しの失敗。

## 確保の失敗の試験の期待の変更

フォルダを変えた後の読み直しに確保が入ったので、確保の失敗の掃引（`eng/coverage.py`の測定ビルド）で、既存の試験の期待が合わなくなった。閾値・除外には触っていない。

測定を流すたびに1つずつ見つかり、5回流した。

| 試験 | 前の約束 | 変えたこと |
| --- | --- | --- |
| `transfer_tests.c`「import allocation failure is typed」 | どの確保が失敗しても「メモリ不足」 | ノートを書いた後の読み直しで失敗したときは「台帳が古い」で、1件追加されている。この結果も受ける |
| `state_tests.c`「published draft is named even when its saved-copy repair fails」 | 初回保存の直後、最初の確保の失敗は検索用の写しの更新で起きる | 試験は変えていない。製品の側で、写しの更新を台帳の同期より先にした（2つは互いに依らない）。試験の意味がそのまま保たれる |
| `state_tests.c`「repaired index can be followed by another copy OOM」 | 保存の最初の確保の失敗は、台帳を書き直した後の写しの修復で起きる | 台帳を書く前に読み直すので、最初の確保は読み直しのもの。失敗させる確保の位置を1から順に探し、「台帳を書いた後の写しの修復で失敗した」回を見つけて確かめる形にした |
| `allocation_tests.c`「transfer note under probe」「first save under probe」 | 結果は成功か「メモリ不足」 | ファイルの操作の後の読み直しで失敗したときの「台帳が古い」も受ける |
| `allocation_tests.c`「trash allocation failure remains typed」 | ごみ箱へ送った後は、確保をせずに削除を採用する | 送った後に台帳を読み直すので、確保が起きる。読み直しに失敗しても削除は採用される（一覧から消え、開いていた文書は閉じる）ことを確かめ、台帳は待つ |

最後の行は、もとの設計の約束（「公開した後の採用は確保しない」）が変わったことを意味する。採用そのもの（メモリの一覧と文書の状態）は今も確保なしで済む。確保が要るのは、その後の台帳の書き込みの前の読み直しだけで、失敗しても採用は取り消されない。

## 不安定な試験（`text_menu_native`）

この枝の全体のCTestで、`text_menu_native`が落ちる回があった（「the menu key closes the body's menu」。本文のメニューを開いたままメニューのキーを押した後、フォーカスが本文に戻ることの確認）。
