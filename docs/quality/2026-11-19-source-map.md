# 2026-11-19 閲覧の段落と原文の行の対応表（#1008 / ADR0116）

## 何をしたか

ADR0106が次の段階とした閲覧の右クリックの「ここを編集」「Markdownとしてコピー」の土台。coreの描画が、ブロックごとの原文の範囲と、閲覧欄に残す段落の記号の数を記録する。
画面には何も出ない（第2・第3段階は予定）。1.5.0の候補には入らず、通常exeへも反映しない（hideの実機確認の対象を変えないため）。

## 試したことと結果

| 段階 | 結果 |
| --- | --- |
| 計画 | 読み取り専用の計画席が、4つの方式（描画と同じ一巡の表、段落の書式に番号、近い見出し、coreで文字位置を数える）を比べ、表を推した。計画はD:/NeNeFolio/agents/source-map-20261119/plan-20261119.md |
| 第0段階の検証 | 隠したRichEditへRTFを流し、生の文字の記号を数えた（probe.c、probe-output.txt）。最後の`\par`は吸収される、表の1行は始まりの印＋CR・セルごとのU+0007・終わりの印＋CR、表で終わる文書は最後のCRが残る、TOMの段落の移動は記号の数と合わない |
| 1つの入口で記録する案 | 段落は次の空行を読んだときにまとめて出るので、行ごとの記録では後の行の分として数えてしまう。各ブロックを出す直前に記録する形にした（コードの行は前の行を終える`\par`の後） |
| 構築の1回目 | 宣言の重複1件と、clang-tidyの上限に4関数（`start_fence`の複雑度、`markdown_blocks_render`の引数5つ、RTFを数える2関数）。記録を別の関数へ出し、引数を`markdown_blocks_options`にまとめ、走査の状態を専用の見出し（`markdown_source_scan.h`）に移した |
| 試験の下書きで見つけた欠陥 | 最初の項目より前に記号があると、番号を0から振ってずれていた。前の分を数えてから振るよう直し、試験を足した |
| 単体試験の登録 | 試験の一覧の関数が長さの上限に掛かった。同じ閲覧のRTFの副産物を確かめる`run_code_copy_tests`の最後から呼ぶ形にした |
| native試験 | 6つの文書で、閲覧欄の生の文字の記号の数（25・32・7・2・1・15）が表の総数と一致。ASCIIのコードの行は、その番号の段落がその行を表示していた。試験の関数の上限（複雑度・引数）と、大域の見本の名前との重なり（`-Wshadow`）を直した |
| 変異 | `\trowd`を数えない変異で、native試験が「the map's total is the pane's marks」（25対22）で落ちた。戻して更新日時を今にし、通ることを確かめた |
