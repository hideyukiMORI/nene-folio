# 2026-11-21 dataフォルダの見張り（#1117 / #1070 / ADR0119の段取り4）

## 何をしたか

Folioを前面にしたまま外（WSL側のLLMなど）でdataが変わったときにも、一覧と開いているノートを読み直すようにした。次の版の変更で、公開した1.5.0には入らない。

- adapters/win32: `data_watch`（`FindFirstChangeNotificationW`でdataの下のサブツリーを見張る。ファイル名・フォルダ名・大きさ・最終更新。ハンドルは外へ出さない）。`data_watch_wait`が、メッセージか変化の知らせのどちらかで戻る。変化で戻った後は、`data_watch_listen`を呼ぶまで次の知らせを待たない。
- app: 入口のループの待ちを`WaitMessage`から`data_watch_wait`へ（`wait_for_work`）。窓が知らせをまとめている最中は、次の知らせを頼まない。見張りは一覧を読む前に張り、張れなければこれまでどおりメッセージだけを待つ。
- ui/win32: `folio_window_data_changed`が、最初の知らせで300ミリ秒のタイマーを掛け、鳴ったら#1112の印（`outside_due`）を立てる。読むのは#1112と同じ道（窓が静かなとき。読むだけ）。
- 背景スレッド・入れ子のメッセージの待ちは足していない（C-013）。

## 設計の判断

| 判断 | 理由 |
| --- | --- |
| 待つ関数と、次の知らせを頼む関数もアダプタに置いた（ADR0119の決定7は「app: 待ちの形」だった） | ハンドルを外へ出すと、`app`と試験がハンドルの扱いを知ることになる。ループの形と、いつ頼むかの判断は`app`に残した。ADR0119の実装の状態に補正として書いた |
| **変化で戻ったら、まとめ終わるまで次の知らせを頼まない**（最初の版は、知らせのたびに頼み直して、タイマーを掛け直していた） | 独立レビューの指摘。最初の版は、(1) 知らせをすぐ出し直す場所で待ちが空回りしてCPUを使い切る恐れがあり（そのあいだタイマーが鳴らないので読み直しも来ない）、(2) 書き込みが300ミリ秒より短い間隔で続くと読み直しが来なかった。いまの形は、どちらも「300ミリ秒に1回まで」になる。そのあいだの変化はOSが覚えていて、頼んだ直後に知らされる（試験で確かめた） |
| 何が変わったかは見ない | 読み直しの部品が「同じなら何もしない」（ADR0119の理由のとおり） |

## 独立レビュー（読み取り専用の席。最初の版のコミット`b19bac3`を対象）

読んで証明できたコードの欠陥は無し。指摘と対応:

| 指摘 | 対応 |
| --- | --- |
| 知らせがすぐ出直す場所での空回り／書き込みが続くあいだ読み直しが来ない | 上の表のとおり、形を変えた |
| 文書が段取りの4を書いていない（コミットの時点。作業木では書いていた）／決定7と合わない／ADR0068が`WaitMessage`のまま | ADR0119に実装の状態と2つの補正を書き、ADR0068に補正を足した |
| 実窓の試験の待ちが、ほかのタイマーで早く戻り、300ミリ秒をまたがずに「出ない」を確かめうる | まとめが終わったこと（`folio_window_data_settling`が偽になった）を待ってから確かめる形にした |
| 見張りを張る前（一覧を読んでから窓ができるまで）の変化を取りこぼす | 一覧を読む前に張る |
| 更新日時を保ったままの書き換えを見逃す | 大きさの変化も見る（同じ大きさで日時も保つ書き換えは見逃す。戻ったときの読み直しが残る） |
| 窓のハンドルが無いときにタイマーを掛けると消せないタイマーになる | ハンドルが無ければ何もしない |
| 実ファイルの試験の最初の確かめが、前の段の遅れた知らせで揺れうる | 最初に静まるのを待つ形にした |

レビューが確かめて問題の無かったこと: 読み直しは読むだけで、自分で知らせを呼び続ける輪は無い（画像のキャッシュはメモリ、錠のファイルは見張りの前に作られる）。保存先の作り直し・改名は、錠のファイルが妨げる。タグの管理・検索・ノート内検索は面の上で動くので、そのあいだは読み直さず、閉じた後に1回読む。入れ子の待ち（ダイアログ・メニュー）の中ではタイマーが印を立てるだけ。`adapters_win32`は`user32`を使ってよい（`eng/architecture.json`）。

対応していないもの（残るリスクに書いた）: 台帳の書き込みに失敗した後の読み直し（#1112からある）、アプリ自身の操作のたびの読み直しの費用、見張りが止まった後に張り直さないこと。

## 試験

実ファイル（`ledger_refresh_native`の`watch`の段、本物のアダプタ）:
- カテゴリの中のファイルを書くと、待ちは「変わった」で戻る。
- 次の知らせを頼むまでは、そのあいだに書いても、待ちはメッセージで戻る。
- 頼むと、そのあいだの変化がすぐ「変わった」で知らされる。
- メッセージを1つ待たせて頼み直しを続けると、待ちはメッセージで戻る（知らせが出たままにならない）。
- ファイルを消しても「変わった」。見張りが無ければ、メッセージだけを待つ。

実窓（`outside_refresh_native`の「前面のまま」の段）:
- 知らせを2回続けて受けると、まとめている最中になり、その場では読まない。
- まとめが終わった後、窓を離れずに読み直され、1行「外部の変更を読み込みました。」。
- 追記してCtrl+S（アプリ自身の保存）の後に知らせを受け、まとめが終わっても、編集表示のまま追記が残り、「このノートは外部で変更されました。」は出ない。

## 変異・検証

結果はこの節とPRの本文に書き足す。

## 残るリスク

- **入口のループ（`main.c`）は自動の試験の外。** 実物のexeで、起動直後のCPU（入力なし20秒。保存を1回した後と、外で書き込みが続くあいだも）と、前面のままの読み直しを確かめる必要がある（hideがいるとき）。ADR0119の段取りの4が求める測定は、まだしていない。
- `MsgWaitForMultipleObjectsEx`（`QS_ALLINPUT`と`MWMO_INPUTAVAILABLE`）は、`WaitMessage`と違い、すでに届いている入力でも戻る。全範囲の`PeekMessageW`が消さない入力の状態があれば空回りする。コードを読んだ限りでは無いが、上の測定でしか確かめられない。
- アプリ自身の保存・星・改名などのたびに、0.3秒後にすべてのカテゴリのフォルダと台帳、開いているノートのファイルを1回読む。外で書き込みが続くあいだは0.3秒ごとに読む。大量のノートや遅い保存先での時間は測っていない。
- 知らせを頼めなくなったら（保存先が外れたなど）、その起動のあいだは張り直さない。変更の通知を出さない場所では、ほかのアプリから戻ったときの読み直しだけになる。WSLの共有の上にdataを置いた場合に通知が来るかは確かめていない（dataがWindows側にあり、WSLから`/mnt/c`経由で書く形も、実機では確かめていない）。
- 台帳の書き込みに失敗して保留になっているとき、読み直しがディスクの台帳を採ると、書けていない変更がどうなるかは追っていない（#1112の「戻ったとき」から同じ。見張りで自動になった）。
- 実窓の試験は本物のタイマーを待つ（最長10秒）。重い機械で鳴らなければ落ちる。
