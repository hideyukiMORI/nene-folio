## hideが見つけたこと（2026-11-22の夜、候補 main `1d7573f`）

エクスプローラからPNGを編集表示の本文へ落とすと、RichEditが画像を埋め込みの物として本文へ入れた。落とすたびに増える。下の1行の知らせは出ず、`images/`にファイルは増えない。ポインタは「コピー」の印。

## 実験: RichEdit自身の投下先を直接呼ぶ

道具: D:/NeNeFolio/temp/20261122/oledrop/probe/ole_probe.c（結果の写しは同じフォルダの`result1.txt`から`result4.txt`）。
見えない窓に`RICHEDIT50W`を作る。`Msftedit.dll`が`RegisterDragDrop`を呼ぶ所を実験の道具の中だけで差し替えて、RichEditの投下先（`IDropTarget`）を受け取り、`DragEnter`・`DragOver`・`Drop`を自分で呼ぶ。マウスは動かさない。クリップボードには触らない。製品のコールバック（`note_pane_ole.c`）を、呼ばれ方を書き出す包みに入れて渡した。OSはWindows 11（10.0.26300）。

| 確かめたこと | 結果 |
| --- | --- |
| 投下先の登録 | 編集できる状態で登録され、読み取り専用へ戻すと外れる（前の実験と同じ）。窓のプロパティ`OleDropTargetInterface`の値は、登録された`IDropTarget`そのものだった |
| コールバックなし・ファイル | 欄へ`WM_DROPFILES`は来ない。親へ`EN_DROPFILES`も来ない。実在するPNGのシェルのデータの物は受け入れられ（`DragEnter`が効果を返す）、`Drop`の中で実験の道具が落ちた（アクセス違反。3回とも）。hideの実機では落ちずに埋め込まれた。**違いの理由は調べていない** |
| コールバックなし・書式つきの文字（RTFだけ） | 書式つきのまま本文へ入った |
| コールバックなし・右クリック | 右ボタンを離すと、欄へ`WM_CONTEXTMENU`が来る |
| コールバックあり・ファイル | `DragEnter`で`QueryAcceptData`（本当に落とすか＝偽）→ `GetDragDropEffect`。`DragOver`は`GetDragDropEffect`だけ。`Drop`は`GetDragDropEffect` → `QueryAcceptData`（真）。「こちらで扱った」（`S_FALSE`）と答えると、効果は「コピー」、本文は変わらず、物は0個。Ctrlを押していても同じ |
| コールバックあり・落とした位置 | `QueryAcceptData`（真）が呼ばれた時点で、選択は落とした点の位置へ畳まれている（偽のときは元の選択のまま）。字の中で点を1画素ずつ動かした8通りで、落とした点の`EM_CHARFROMPOS`と同じ位置だった。元に選択の範囲があっても同じ |
| コールバックあり・文字だけ | 形式を`CF_UNICODETEXT`にして受けると、落とした位置へ文字が入る。効果は、コールバックなしと同じ（既定は移動、Ctrlでコピー） |
| コールバックあり・書式つきの文字（RTFだけ） | 受けない（効果は「落とせない」） |
| コールバックあり・右クリック | **右ボタンを離すと、RichEditは`GetContextMenu`を尋ね、欄へ`WM_CONTEXTMENU`は来ない。** 閲覧表示（読み取り専用）でも同じ。前の席の作りかけは、このままだと右クリックのメニューが出なくなっていた |
| 右ボタンを離した知らせを、RichEditでなく窓の既定の処理へ渡す | `WM_CONTEXTMENU`が、押した点の画面の座標で来る。RichEditは右ボタンでポインタをつかんでいない。その後の左クリックでキャレットが動く |
| 参照数 | 窓を壊すと、RichEditはコールバックの参照を放す（包みの数が元へ戻った） |
| `IRichEditOle::ImportDataObject`へファイルを渡す | コールバックがあっても、実験の道具が落ちた（コールバックは呼ばれていない）。製品はこの入口を呼ばない |

前の席の記録（#1149の品質記録の「できなかったこと: 窓のプロパティの値を入口として呼ぶと落ちた」）は、プロパティの値が呼べないのではなく、コールバックなしのRichEditへファイルを落とすと落ちる、のほうだった可能性が高い（確かめてはいない）。

## 入れたもの（最初の形。レビューの後に変えた所は、その場に書いた）

- `src/ui/win32/note_pane_ole.{h,c}`（新規）: `IRichEditOleCallback`の実装。公開するのは「作る関数」`note_pane_ole_create`だけ。
  - 投下（`RECO_DROP`）にファイルの並びがあれば、`S_FALSE`。本当に落とされたときは、並びの写し（頭の大きさと名前の始まりを確かめ、末尾に0を足したもの）を、選択の始まりの位置と一緒に、主窓の`folio_message_files_dropped`へ送る。欄の`WM_DROPFILES`の道と同じ行き先で、取り込みの処理は1つのまま。
  - 投下がファイルでなければ、形式を`CF_UNICODETEXT`にして`S_OK`。
  - 欄か主窓が入力を止めているあいだの投下は断る（`E_FAIL`）。レビューの後: 文字の投下は、貼り付けと同じ1つの判定（準備中・変換の途中・着色の錠・読み取り専用も）で断る。
  - 投下でない問い合わせは`S_OK`のまま通す。レビューの後: 貼り付け（`RECO_PASTE`）は、形式を`CF_UNICODETEXT`にして`S_OK`。
  - `GetNewStorage`は`E_NOTIMPL`（埋め込みの物の置き場を渡さない）。`QueryInsertObject`は`S_OK`（下の「途中の失敗」。断ると、閲覧表示の画像が入らなくなる）。`GetDragDropEffect`は、ファイルが上にあるあいだだけ「コピー」（送り手が許していなければ「落とせない」）。文字の投下は`E_NOTIMPL`で既定のまま。欄からのドラッグは`S_OK`で、渡された効果を変えない。`GetClipboardData`・`GetInPlaceContext`・`ContextSensitiveHelp`・`GetContextMenu`は`E_NOTIMPL`、`ShowContainerUI`・`DeleteObject`は`S_OK`。
  - データの解放は、最初の形では自作だった（持ち主がいればその`Release`、いなければ`GlobalFree`）。レビューの後: `ole32`の`ReleaseStgMedium`を呼ぶ。`ole32`は`nenefolio_window`に前から結ばれていて（`CMakeLists.txt`と`eng/architecture.json`の`ui_win32`）、自作する理由は無かった。OSライブラリは足していない。
- `src/ui/win32/note_pane.c`: 欄を作るときにコールバックを渡す（`prepare_drop`）。右ボタンを離した知らせだけ、RichEditでなく窓の既定の処理へ渡す（`pane_forward`）。
- `src/ui/win32/folio_message.h`: メッセージの説明（送り手が2つになった）。
- `tests/win32/image_status_tests.c`: 下の試験。
- 文書: ADR0120、この記録、WVR-0002と索引。

## 前の席の作りかけから変えた所

- 位置の決め方: 作りかけは、ポインタの今の位置（`GetCursorPos`）を、写した並びの中の点へ書き込み、欄へ`WM_DROPFILES`を送っていた。実験で、RichEditが落とした点へ選択を畳んでから尋ねることが分かったので、選択の始まりを使い、主窓へ直接送る形にした。ポインタの位置は、落とした後に動くとずれ、試験でも決まった値にならない。
- 右クリック: 作りかけは`GetContextMenu`が`E_NOTIMPL`を返すだけで、右クリックのメニューが出なくなる状態だった（既存の試験は`WM_CONTEXTMENU`を直接送るので、気づけない）。`pane_forward`と試験を足した。
- 入力を止めているあいだの投下を断る。ファイルの印は、送り手が許した効果の中から選ぶ。欄からのドラッグの問い合わせは`S_OK`にした（`E_NOTIMPL`のままでも動く見込みだが、確かめられないので、広く使われている実装と同じ答えにした）。
- 作りかけは構築が通っていなかった（`DROPFILES`の型が見えない）。引き継いだ時点では、ヘッダが足されて通る状態になっていた。
