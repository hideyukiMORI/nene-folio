## #41（現在のmdだけの正規表現置換・FR-023）— 実測・ADR 0028・実装の途中

- **正規表現エンジンの実測probe**（`out/design/2026-09-22/replace-probe/`・101項目成功）。Windows同梱の`icu.dll`（`uregex`）をclang-cl + `icu.lib`で結べる
  （測定機はICU 72.1 / Unicode 15.1。`icu.dll`は1903以降、仕様の最低環境2004以降に含まれる）。位置はUTF-16のコード単位で`EM_EXSETSEL`と1対1、
  サロゲートペアは`.`に1件。既定の行端の扱いでCRは行端（`UREGEX_UNIX_LINES`は付けてはいけない）。利用者が打つ`\n`はCRに一致しない。
  `(?i)`はfull case folding（全角英字も畳む・既存の検索とは意味が違う）。壊れたパターンは`UErrorCode`と`UParseError.offset`で位置が分かる。
  **ICUの置換文字列の文法は利用者に見せられない**（`\n`が`n`・`$100`がエラー・末尾の`\`が消える）。ゼロ幅一致で無限ループしない。上限は`uregex_setTimeLimit`のsteps
  （時刻を読まない・測定機で1 step≒0.15ms）。1.18MiBでliteralの全一致1.5ms・`(\w+)-(\w+)`46ms。`uregex_*`は非決定名に無く、`eng/symbols.py`はcore/applicationだけ検査する。
- **ADR 0028の草案を書き、現行コードに照らした読み取り専用の批評を挟んでから受理**（`2b58e63`。ADR 0016に入力面の欄が集合になる補正節）。批評で直した点:
  引数4つ（C-012）を超える署名が3本あった→`regex_request` / `regex_matches` / `replace_request` / `replace_apply`に束ねる（ADR 0023で一度起きた失敗）、
  `:%s/a/b/g`は空白で切った1語の別名照合では解けない→別名照合の前に「`%s`で始まり直後が英数字でない」で判定、
  ICUはOS同梱なので`runtimeDependencies`ではなく`platformLibraries`が正本で、CODING_RULES第5節の「kernel32以外をimportしない（R1）」は既にuser32等で崩れている→文言を直す、
  入力面のEDITは1つ前提でTabで2つ目へ移ると欄が閉じる→「自分の欄」を集合に、`apply`にanchorが無い→`note_search_span`を受ける、
  下見を捨てる契機の列挙は10か所以上に散って漏れる→写しに宛先を添えて適用時に照合（`REPLACE_STALE`）、`regex_match.h`はcoreに置かないとcoreが読めない、
  stepsの上限はadapterの定数。`folio_state_create`は4引数で飽和し、#38が`struct folio_ports`に束ねる。
- 決定の要点: エンジンはOS同梱のICUをadaptersに閉じる（`nenefolio_system_link(nenefolio_adapters icu)`）／portは1回の呼び出しで閉じる粗い`scan`／
